## 第 1 章：最终功能与已经确认的规则

### 1.1 最终要做成什么

系统里有三组相互配合的功能：

1. **项目业务模块**：项目列表、新建页、编辑页、详情页、审批页。
2. **系统管理里的审批配置**：业务角色配置、角色成员管理部门配置、流程图设计、校验、发布版本、绑定项目模块。
3. **审批工作台**：我的待办、我的已办、审批记录、驳回和允许范围内的撤回，以及缺人阻塞后的恢复。

基本操作路径：

管理员配置人员与角色 → 画流程图并发布 → 绑定项目模块 → 创建人创建项目并提交 → 系统分配待办 → 审批人处理 → 项目通过。

“流程配置”放在系统管理菜单下，不等于所有运行代码都应塞进系统管理模块。页面菜单位置和后端业务分层是两件事。

### 1.3 人员与部门规则

1. 节点可以多选系统角色和业务角色，结果取并集、按用户 ID 去重，不是求交集。
2. 系统角色：从现有角色的有效成员中找人。
3. 业务角色：一个稳定编码对应一种找人规则，例如当前项目的 IT 经理、业务经理、创建部门负责人。
4. 业务角色不是把所有模块里的同类经理预先维护成一个全局成员名单。
5. 部门负责人角色的每位成员可以配置多个管理部门。关系必须精确到“角色+人员+管理部门”。
6. 项目创建时记录创建人的部门。以后创建人调岗，不修改这份记录。
7. 寻找部门负责人时，先匹配该部门；没有有效负责人，再逐级向上找；找到第一个有人负责的层级就停止。
8. 同一层级匹配多人时，全部加入本节点候选集合，再应用节点的或签/会签规则；不自动加入更高层负责人。
9. 提交前检查发布版本里的全部审批节点，包括条件分支暂时不会走到的节点。任何节点最终无人，拒绝提交并定位节点。
10. 提交预检查不冻结人员。真正进入节点时再解析一次，之后本次节点的审批名单固定。
11. 节点进入后角色成员变化，不自动替换已生成待办；下一次重新进入才重新找人。
12. 运行时重新解析无人，实例阻塞，不能自动通过。补齐配置后由有恢复权限的管理员重试，保留操作记录。
13. 创建人也是候选人时，可以审批，但必须手动操作，不自动通过。

**“有权限查看部门单据”不等于“必须参与所有下级部门审批”。** 查看权限包含下级部门；审批找人采用最近有负责人的一级。

### 1.4 流转规则

| 事项 | 已确认规则 |
| --- | --- |
| 串行 | 前一节点通过才激活后一节点 |
| 并行 | 多条分支同时执行，全部完成才允许汇合继续 |
| 条件分支 | 只走一条，按明确优先级命中第一条，必须有默认分支 |
| 或签 | 本次节点任意一人同意即通过；节点尚未完成时，一人驳回即否决 |
| 会签 | 本次节点全部候选人同意才通过；一人驳回即否决 |
| 节点完成后 | 其余待办关闭，不能再审批或追溯否决；并发操作由后端串行判定 |
| 驳回时 | 暂停实例中的其他待办；不能趁流程退回继续审批 |
| 主动撤回 | 只有尚无人作出审批操作时，创建人才可撤回 |
| 流程版本 | 项目首次提交绑定版本；以后发布新版本不影响它，驳回重提仍用原版本 |
| 模块绑定 | 项目模块绑定一个当前启用的流程，创建人不手选；不同项目类型在图内走条件分支 |

“固定第一版”指首次绑定的那个版本，不是所有将来项目永远使用全局第 1 版。

### 1.5 两种驳回，不能实现成同一个改状态操作

正常流程例子：`起草 → A → B → C → D → 结束`。

**模式一：驳回重走。**

- 当前审批人选择该模式，不允许选择目标节点。
- 返回起草，只有创建人能修改和提交。
- 重新提交后，从图的入口重新判断并执行，例子中就是从 A 开始。
- 旧审批保留为历史，但不能直接充当新一轮的通过结果。
- 清理旧轮次的活跃任务、并行到达记录、定点返回安排，不能删历史。

**模式二：定点返回，处理后回到原驳回节点。**

- D 退到起草：创建人任意修改字段并提交 → 直接重新进入 D，跳过 A/B/C。
- D 退到 B：B 的审批人重新处理 → 直接重新进入 D，跳过 C；不经过创建人提交。
- D 退 B，B 又定点退起草：起草 → B → D，逐层恢复，不能丢失 D。
- 返回目标限起草、当前可回退路径上已经到达的审核节点；不能选未来节点。
- **不能跨到另一条并行分支。** 允许同分支的历史审核节点、该分支之前已经过的公共祖先审核节点。
- 后端根据实际执行上下文计算目标清单；前端不能任意传一个历史节点 ID 就获准跳转。
- 汇合后的节点不能仅因某个并行内部节点曾执行过，就把它当成同一分支祖先；需要按分支作用域校验。

**定点返回后的资料与并行：**

- 只有回到起草才允许修改；其他审核环节资料只读。
- 起草可以改全部字段，即使改变条件或经理，也仍直接返回原驳回节点，不补走被跳过的节点。
- 已通过的其他并行分支保留原通过结果，不重审。
- 审批记录必须保留它实际审批的资料版本，不能暗示旧结果批准了新资料。
- 此后尚未执行的条件节点，使用最新提交资料判断；不追溯改写已经走过的路线。

### 1.6 查看、修改和审批权限

| 身份/入口 | 能查看什么 | 能修改什么 | 能执行什么 |
| --- | --- | --- | --- |
| 创建人，项目列表/详情 | 自己创建的项目 | 仅起草状态的自己的项目 | 创建、保存、提交、符合条件的撤回、删除自己的草稿 |
| 部门负责人，项目列表/详情 | 管理部门及全部下级部门的项目 | 不因负责人身份获得编辑权 | 只有实际获得待办才可审批 |
| 超级管理员，项目列表/详情 | 全部项目 | 不自动代替创建人编辑 | 配置与必要恢复按专门权限；不代替候选人投票 |
| 普通审批人，待办/已办入口 | 自己任务关联的单据 | 不能修改业务字段 | 仅处理自己的有效待办；已办只读 |
| 页面里的两类经理 | 不单因字段中被选中而增加项目列表可见范围 | 无额外编辑权 | 实际获得任务后按任务权限处理 |

项目属于哪个部门，统一依据创建时记录的创建人部门，而非业务部门，也非创建人的当前部门。

普通审批人从任务入口看单据，不要求先有项目列表权限，但也不因此获得通用项目详情的全局授权。

### 1.7 第一版范围

包括上述完整主流程、草稿软删除、审批轨迹和资料留痕、缺人后的配置修复与恢复。

暂不包括：转交、加签、抄送、催办、超时自动处理、已通过项目作废、移动端适配、附件、金额预算和汇率、导入导出、消息推送。后几项是本计划未承诺的独立扩展，不为实现当前需求强行加入。

无期限催办、循环审批路线、任意脚本条件不在当前范围。正常流程图采用可验证的结构化分支；业务上的反向处理由驳回机制承担，不靠在画布上画回环。

### 1.8 实施默认值与仍需补充的业务数据

以下不是用户额外确认过的业务要求，而是本文为便于实施提出的明确默认值，可在对应步骤调整：

- 项目名称建议最多 200 字，不默认全局唯一；项目唯一标识是 ID。不要照抄岗位名称唯一校验。
- 第一版按九项必填实现完整草稿保存；不完整的分步暂存是后续独立需求。
- 业务部门先由创建人明确选择，不把“默认带出其部门”写成既定需求。
- 两类经理从允许发起项目的用户可查询的最小人员目录中选择有效用户，不强制本部门；只返回 ID、姓名及必要部门信息，不返回手机号等多余字段。
- 同一人可同时担任两类经理；本节点去重，但不同节点仍分别生成任务，不自动跳过重复审批。
- 审批动作指手动同意或驳回；查看详情不算审批。撤回的判断不因重走而清除既有审批历史。
- 恢复已有暂停任务，不视为重新进入节点，保留原候选名单；若是重新进入驳回目标或原驳回节点，则创建新的一次节点执行并重新解析人员。
- 暂停期间资料变更，恢复的待办显示新资料与差异；审批动作绑定用户实际看到的版本。已通过的分支不变；未重新进入的节点既有投票也不暗中抹除，记录各票对应版本。
- 默认不物理删除用户、部门及被历史引用的配置；显示快照和稳定 ID 防止改名、停用破坏历史。
- 部门快照固定部门身份，不冻结整个组织树。本版按当前有效组织树计算上下级；组织撤并需人工处理，不自动把历史单据迁入别的部门。
- “只删除自己的草稿”包含退回起草的单据；必须同时终止其挂起实例/任务，保留审批历史，不能只隐藏项目主表。
- 节点名单固定不等于停用账号还能操作。每次审批仍校验用户有效；会签成员停用导致无法完成时，暂停并报告，不静默减人或自动通过。第一版不做任意转交，需走受控修复/重走策略，不冒充已有“缺少下一节点审批人”恢复就能换掉当前会签人。

正式配置前还需补齐三个字典的真实选项、部门负责人系统角色的稳定标识、流程配置/恢复权限实际授予谁，以及测试账号。它们不妨碍先设计结构，缺少时不得用猜测值上线。

### 2.2 必须避免的六个误区

**误区一：现有 workflow 就是审批引擎。**

[task/storage/workflow/model.py](/Users/yixin/work/FastapiAdmin/backend/app/modules/task/storage/workflow/model.py) 存的是文件传输源、目标及传输参数。可以参考“布局与业务配置分开保存”的思想，不能混用其表和运行逻辑。

**误区二：通用 CRUD 的注释说不做权限，所以新业务只要在 Service 做就行。**

[base_crud.py:38](/Users/yixin/work/FastapiAdmin/backend/app/core/base_crud.py:38) 的类注释写“不按这些字段过滤数据”，但 [_build_conditions:338](/Users/yixin/work/FastapiAdmin/backend/app/core/base_crud.py:338) 实际调用 `Permission._permission_condition()` 并加入查询。

这是注释与实现冲突，**必须按当前实现设计**。新业务不能先被通用权限排除，再指望 Service 追加条件把它找回来。

新项目查询采用专门的 ProjectAccessPolicy 和显式查询，通用 CRUD 只复用明确不会重复过滤的部分。不伪造超级管理员身份、不把角色 `data_scope` 一律改成全部、不为方便修改全局基础设施行为。

**误区三：现有数据权限等于我们需要的部门权限。**

[permission.py](/Users/yixin/work/FastapiAdmin/backend/app/core/permission.py) 的部门范围主要来源于当前用户自身部门，普通模型的部分判断会沿 `created_by` 取创建人的当前部门。我们的规则是“负责人管理部门范围 + 项目创建部门快照”，不能直接套用。

**误区四：`sys_role_depts` 能放每个人的管理部门。**

该表只有角色和部门，没有人员维度。且 [RoleService.set_permission](/Users/yixin/work/FastapiAdmin/backend/app/modules/system/role/service.py:156) 当前明确清空这一旧关联。角色模型中关于 `data_scope=5` 的注释、基础模型中旧的 1～5 范围说明，也与当前 1/2/3 实现不一致。必须新增独立关系，不能借旧字段硬塞。

**误区五：所有新表直接继承 ModelMixin 就安全。**

[base_model.py](/Users/yixin/work/FastapiAdmin/backend/app/core/base_model.py) 的默认索引含 `status`、`is_deleted`。没有这些列的关系表、运行表应使用 `MappedBase` 或明确覆盖表索引，不能盲目继承。子类自定义 `__table_args__` 时也要显式核对哪些索引实际保留。

**误区六：修改初始化 JSON，下次启动就会补齐现有库的菜单字典。**

初始化逻辑是表已有记录就整体跳过。已有环境要走增量配置步骤；新空库还会按模型建表后标记迁移 head，因此不能只把必要初始配置写在一次性数据迁移里。必须同时覆盖“全新环境”和“已有环境”，以稳定编码幂等补齐指定配置。

## 第 3 章：架构怎样拆，为什么这样拆

### 3.1 三部分分工

**项目业务：管单据。**

负责九个字段、经理成员、创建部门快照、起草权限和资料版本。不自己实现“B 通过后去哪”。

**人员解析：管找谁。**

接收业务类型、单据、节点规则和当前组织配置，返回候选人及解释，例如“由财务部上查到集团财务中心，命中两名负责人”。不自己决定流程跳转。

**流程引擎：管下一步。**

负责版本、节点执行、待办、或签/会签、分支、汇合、暂停、重走、定点返回。不直接读取 `ProjectModel.it_manager_ids` 之类业务字段。

不新增工作流服务器、消息队列或新的数据库。第一版在现有 FastAPI 应用内做模块化实现，运行事实持久化在现有业务数据库；Redis 不是审批进度的唯一存储。

### 3.2 建议代码位置

下面是**拟新增路径，不代表文件已经存在**。每个 Python 包需有合适的 `__init__.py`。

```text

backend/app/modules/workflow/
```

项目模块顶级菜单名称可以在菜单配置时决定，不影响这里的后端领域拆分。

### 3.3 业务角色如何做到“通用但不假装零代码”

统一接口建议：

- `BusinessAdapterRegistry`：按 `business_key` 找到单据适配器。
- `ProjectWorkflowAdapter.build_context(project_id, revision_id)`：生成允许使用的业务上下文。
- `ResolverRegistry.resolve(rule, context)`：按稳定策略编码找人。

第一版至少提供：

| 来源 | 规则示例 | 实际取值 |
| --- | --- | --- |
| 系统角色 | `SYSTEM_ROLE` + 角色 ID | 当前有效角色成员 |
| 业务角色 | `PROJECT_IT_MANAGER` | 当前提交资料中的 IT 经理集合 |
| 业务角色 | `PROJECT_BUSINESS_MANAGER` | 当前提交资料中的业务经理集合 |
| 业务角色 | `CREATOR_DEPT_MANAGER` | 创建部门快照 + 指定负责人角色 + 最近一级向上查找 |

为减少每个模块重复代码，可以提供“从适配器暴露的用户集合中取人”“按部门找角色成员”这样的通用策略。不同模块映射到自己的字段或关联表。

管理员可以配置已有策略对应的业务角色；不能随便填写 Python 导入路径、SQL 或脚本来执行。全新找人逻辑仍需要开发、测试和注册策略，这一点不伪装成完全零代码。

发布版本要保存当时业务角色的规则编码和配置快照，不能因为后来修改“业务角色”的含义，就悄悄改变旧流程规则。角色成员、单据人员仍按进入节点时的数据动态解析；配置快照与成员冻结不是一回事。

### 3.4 正常流程图与运行中的“节点执行”是两层

图上的 D 是一份节点定义。第一次到 D、退回后第二次到 D，是两次不同的节点执行。

必须保存 `node_visit_id`，不能只用 `node_key=D` 标识所有历史，否则会把第一次的同意、驳回和第二次的待办混在一起。

同理：一次实例可能有多轮重走；一轮里又可能有并行分支和多次定点返回。不能只在项目表放一个 `current_node_id` 就认为实现了这些能力。

## 第 4 章：数据库设计草案

这里是逻辑设计，列出关键字段和约束；实际字段类型、外键命名、索引及迁移在对应步骤审核。**不要求第一天一次建完所有表。**

### 4.1 项目与组织配置

| 拟建表 | 解决的问题 | 核心字段与约束 |
| --- | --- | --- |
| `biz_project` | 当前项目资料与入口状态 | 九个业务字段中的标量字段、`creator_user_id`、`creator_dept_id`、`status`、`current_revision_id`、`lock_version`、软删除/审计字段；创建人和部门快照不可由更新接口修改 |
| `biz_project_member` | 两类经理的多选 | `project_id,user_id,member_type`；三者联合唯一；不能把多个 ID 拼成逗号字符串 |
| `biz_project_revision` | 提交资料及修改留痕 | `project_id,revision_no,payload,editor_id,reason,created_time`；保存九字段、经理名单及展示名称快照；项目内版本号唯一，历史内容不可覆写 |
| `sys_user_role_managed_dept` | 每个角色成员管理哪些部门 | `role_id,user_id,dept_id` 联合唯一；必须有真实用户角色关联；移除角色成员时同步处理当前管理范围并记审计 |
| `wf_business_role` | 给画布选择的业务角色目录 | `code,name,business_key,resolver_key,resolver_config,status`；编码唯一；不把可执行脚本放入配置 |

项目身份使用独立的稳定 `creator_user_id`，不要只依赖可能因外键置空而丢失语义的通用 `created_id`。审计字段继续记录实际操作者；历史快照保留必要名称，不保留密码等敏感信息。

字典当前字段保存稳定 value，历史资料版本同时保存当时标签，避免字典改名改变历史展示。删除或停用某个字典项不能让旧详情无法打开；新的提交则按当前有效性校验。

### 4.2 流程定义与发布

| 拟建表 | 作用 | 关键内容 |
| --- | --- | --- |
| `wf_definition` | 一条流程模板的身份 | 稳定编码、名称、业务类型、启用状态、当前发布版本引用 |
| `wf_definition_version` | 草稿版与不可变发布版 | `definition_id,version_no,lifecycle,layout,content_hash,published_by,published_time`；模板内版本号唯一 |
| `wf_node_definition` | 节点业务配置 | `version_id,node_key,node_type,approval_mode,assignee_rules,scope_config`；版本内 node_key 唯一 |
| `wf_edge_definition` | 连线与条件 | `version_id,edge_key,source,target,priority,is_default,condition_ast`；端点必须属于同一版本 |
| `wf_module_binding` | 项目模块提交用哪个模板 | `business_key,definition_id`；每个业务模块只允许一个有效默认绑定；发布指针在首次提交事务内一致读取 |

画布 `layout` 只管坐标、缩放、样式等展示信息。节点、条件、角色等执行配置以节点/边明细为准。需要缓存编译结果时，只能由这份事实生成，不再维护第二份可独立编辑的业务 JSON。

发布后不允许原地改节点和边。修改先复制成草稿新版本，校验后发布。已有项目仍引用旧版本记录；停用模板只影响新发起，不让旧实例突然找不到定义。

### 4.3 流程运行

| 拟建表 | 作用 | 为什么不能省成一个状态字段 |
| --- | --- | --- |
| `wf_instance` | 一张单据的流程实例 | 保存 `business_key,business_id,definition_version_id,state,has_approval_action,lock_version`；业务单据与实例关联唯一，防重复发起 |
| `wf_round` | 重走/撤回再提交后的执行轮次 | `instance_id,round_no,cause,submitted_revision_id,state`；旧轮次保留但不参与新一轮完成判断 |
| `wf_execution_token` | 图中当前有哪些执行路径 | 所属实例/轮次、分支路径、作用域、当前位置、状态；并行时可以有多个活跃位置 |
| `wf_parallel_scope` | 一次并行拆分的具体上下文 | 分叉/汇合节点、父作用域、预期分支集合、状态；同一图上并行块被重走时不能混用 |
| `wf_join_arrival` | 哪些分支已经真正到达汇合 | `round_id,scope_id,branch_key` 唯一；防止重复请求把一个分支算两次 |
| `wf_node_visit` | 某节点本次被执行 | 定义节点、token、执行序号、审批模式、候选人/来源解释、进入资料版本、状态；返回重审创建新的 visit |
| `wf_task` | 具体到人的待办 | `node_visit_id,assignee_id,state,decision,decision_revision_id`；visit 内每个用户唯一；待办索引以 assignee/state 为主 |
| `wf_return_context` | 定点返回与嵌套返回链 | 父返回上下文、原驳回节点/作用域、目标、恢复位置、暂停快照、处理状态；不能只存一个 return_node_id |
| `wf_action_log` | 不可变业务操作记录 | 操作人、动作、实例/轮次/visit/task、资料版本、意见、前后状态、时间、关联命令 |
| `wf_command` | 命令幂等与请求追踪 | 操作人、命令类型、幂等键、请求摘要、结果引用；唯一约束防重复同意、提交、恢复 |

表数量体现本需求确实包含一个小型审批引擎。可在物理设计时合并职责紧密的表，但不能省掉实例/轮次/本次节点执行/具体任务/分支作用域/返回链这些逻辑身份。

### 4.4 状态分开表达

**项目页面建议状态：** 起草、审批中、退回待修改、流程阻塞、已通过、已撤回。退回待修改在操作权限上属于起草，来源原因需要显示。

**实例状态：** 运行中、等待起草处理、返回处理中、阻塞、已通过、已撤回、因删除草稿终止。

**节点执行状态：** 活跃、暂停、通过、驳回、取消、阻塞。

**任务状态：** 待处理、暂停、已同意、已驳回、因节点结束关闭、因轮次结束取消。

不要用用户/岗位里“0 启用、1 停用”的含义来解释业务审批状态。采用明确枚举；若使用通用 `status` 列，也必须定义本业务自己的含义。

### 4.5 两种版本和一份部门快照

- **流程版本**：控制节点、连线、条件和审批规则；首次提交绑定。
- **资料版本**：控制这次提交/这张审批票看见的是哪份项目数据；每次提交及必要保存生成不可变快照。
- **创建部门快照**：项目创建时固定，用于负责人解析与项目归属。

三者不能共用一个 `version` 字段。并发用的 `lock_version` 又是第四种技术用途，不是业务资料版本。

## 第 5 章：关键命令怎样执行

本章是拟实现的行为，不是当前已存在的函数。

### 5.1 创建草稿

1. 校验当前用户具备创建入口权限。
2. 校验九字段、经理集合、字典和部门。
3. 从认证用户读取创建人及其当前部门；部门缺失时明确报错，不能让前端代填部门快照。
4. 写项目与经理关系，记录第一份资料快照。
5. 返回草稿；不创建审批任务，不提前绑定一个会随草稿编辑失真的流程版本。

### 5.2 首次提交

1. 锁定项目，确认当前操作者是创建人、项目可提交、请求版本没有过期。
2. 读取模块绑定及当前已发布启用版本；已绑定过的项目改读原版本。
3. 构建本次提交资料上下文。
4. 检查全部审批节点配置是否合法、各节点最终候选集合是否非空；返回所有缺人节点的定位信息。
5. 检查失败则不创建运行实例/待办，不改变成“审批中”；保留此前成功保存的草稿。
6. 成功后，在同一事务绑定流程版本、生成资料提交快照、实例/轮次、初始执行路径与首批待办、操作记录。
7. 即便刚做过全图预检查，真正激活节点也调用同一解析服务，保存本次名单和解析解释。

预检查不应因为当前只有一条条件路径会命中，就跳过其他配置分支的无人检查。未走节点只检查、不创建任务。

一个节点选多个来源时，以最终合并候选集合非空作为“有人”的门槛；每个来源的命中结果分别展示。失效的角色引用或非法业务规则属于配置错误，不能被别的来源有人掩盖。

### 5.3 同意

1. 锁定实例、节点执行和待办；所有引擎命令采用一致加锁顺序。
2. 检查当前账号有效、任务属于操作者、实例允许操作、任务仍待处理。
3. 校验页面提交的资料版本，避免打开旧页面却批准了刚修改后的资料。
4. 保存本人的决定及实际审阅资料版本，记录第一次审批动作。
5. 按本次节点的或签/会签规则判断是否完成；不实时替换候选名单。
6. 未完成则等待；完成则关闭本节点剩余任务，按正常图或返回上下文继续。
7. 下一节点重新找人；若此刻无人，保存“本节点已通过+实例阻塞+阻塞原因”。不能抛一个导致整次事务回滚的普通异常，又在页面声称当前审批成功。

审批提交中出现业务阻塞，可以返回成功的审批结果和明确的阻塞状态；真正数据库错误则整体回滚。必须区分这两种情况。

### 5.4 并行拆分与汇合

- 拆分时生成一个具体的并行作用域及预期分支集合，再生成各分支 token。
- 每条分支完成后登记一次到达；唯一约束防重复计数。
- 只判断当前轮次、当前作用域的预期分支，不数整张图“有几个节点通过”。
- 全部到达后，原子地只激活一次后继节点。
- 条件分支的未选路线不是“未完成并行分支”。条件汇合和并行汇合必须有不同语义。

### 5.5 驳回重走

1. 验证本人当前待办，保存驳回意见与资料版本。
2. 暂停实例中其他待办，关闭被驳回节点本次执行。
3. 记录需要重走，项目回起草，只有创建人可修改。
4. 再提交仍用原流程版本，并再次校验全图人员。
5. 新建轮次，从图入口开始；旧轮次任务失效、旧并行上下文及返回链不参与运行。

### 5.6 定点返回

1. 由后端生成合法目标清单，校验同分支/公共祖先、已到达、当前上下文有效。
2. 保存原驳回位置、目标位置、分支作用域、当前返回链父项和应暂停的任务。
3. 暂停其他可审批任务，只激活返回目标的处理链；如果连目标任务也一律暂停，就永远无法完成返回。
4. 目标是起草：等待创建人修改并提交；目标是审核节点：重新进入该节点，生成新 visit、新候选人与待办。
5. 目标处理完成，不走它在正常图中的后续边，先按返回链重新进入原驳回节点。
6. 原驳回节点也新建一次执行，重新找人，旧的驳回票及其他票仅留历史。
7. 原驳回节点本次通过后，消费相应返回上下文，恢复应继续的其他路径，继续正常流转。
8. 有嵌套返回时从最内层恢复；仍有外层暂停原因的任务不能提前开放。

**资料变化不触发回头重算历史路线。** 已通过分支保留；恢复的未处理任务保留原名单并显示新资料差异；未来节点使用新提交资料。返回目标的重新审批不会向原并行汇合重复发送一次旧分支到达信号。

### 5.7 撤回、删除草稿和恢复

- **撤回**：创建人、实例未有任何手动审批动作；锁定后取消当前任务并回到可编辑起草。再次提交按新轮次从入口开始，仍用该项目已绑定版本。第一版不把撤回做成删除实例后重新绑定最新流程。
- **删除草稿**：只有创建人且当前处于可编辑起草；软删除项目，原子终止相关挂起实例和任务并记录原因；不删除审批历史。通过待办/已办访问时也必须显示终止状态，不能让旧链接继续审批。
- **缺人恢复**：仅授权管理员在补齐人员配置后，重试确切的阻塞节点，重新解析成功后原子激活一次；不修改项目字段，不跳过审核，不全局重置已完成节点。
- **固定名单成员失效**：不能自动删除会签票使节点通过。第一版需明确提示并保留现场；受控处理方案要在该异常用例验收时确认，不暗中实现转交。允许的最低安全行为是保持阻塞，而不是自动完成。

## 第 6 章：按真实开发顺序逐步实施

每一步按“整体功能 → 已有前提 → 一个新机制 → 实施 → 验收”的顺序带学。下列新函数名是建议命名，开工时如有调整，会同步维护阅读导航。

### 第 0 步：保存现状，准备隔离验证条件

**功能：** 确保开发新模块不会覆盖你已有改动，或因热重载意外修改正在使用的数据库。

**前提：** 主要需求已确认；本计划是待评审设计。

**新机制：** 代码、迁移文件和数据库版本是三个需要分别核对的对象。

**具体做什么：**

1. 记录当前 Git 状态、服务进程及所用环境标识；不输出密码和连接凭据。
2. 阅读并保留你现有 CRUD、响应、岗位等修改，不随任务一起格式化或重构。
3. 在明确授权的开发/测试环境查询数据库实际迁移版本；本次尚未做此检查。
4. 明确开发数据备份和恢复办法；优先使用与业务数据隔离的测试库。
5. 检查热重载和自动迁移触发条件；不擅自停服务、切连接、重建容器。
6. 记录本功能涉及目录，后续每步只动这些文件。

**产出：** 开发基线记录、环境与数据保护清单。

**阅读起止：** 现有 `InitializeData.init_db` → `__apply_migrations`，看到自动迁移条件即停。先跳过种子明细、Redis、调度器。

**操作与预期：** 先只查看 Git 和迁移文件；环境未准备好时仍可继续设计，但不能宣称已验证数据库迁移。

**第一排查点：** 迁移多出文件时，先查是否触发了 dev 自动迁移/测试布局，不先删文件。

### 第 1 步：冻结规则、画页面操作清单和状态转换表

**功能：** 明确每个按钮做什么，避免先建表后不断补字段。

**前提：** 第 1 章规则已确认，剩余默认值已公开列明。

**新机制：** 状态转换必须有“谁、什么状态、什么条件、变成什么”。

**具体做什么：**

1. 为创建、保存、提交、同意、两类驳回、撤回、删除、恢复逐一列权限和前置状态。
2. 画项目列表、新建、详情、审批、配置页的内容清单；先不追求高保真画布。
3. 整理固定样例：串行 A/B/C/D、双分支并行、采购条件分支、逐级返回。
4. 明确历史、当前状态、最新资料和历史审批版本在页面上分别怎么显示。
5. 将第 1.8 节默认值列入评审，不冒充用户已确认内容。

**产出：** 本计划的业务基线、操作权限矩阵、状态转换清单、验收样例。

**阅读范围：** 先读本文 1.4～1.6；暂不读引擎类和数据库锁。

**验收预期：** 同一场景能明确说出下一步是谁处理、能否改字段、哪些分支暂停；不出现“看情况”但无规则。

**第一排查点：** 行为说不清时先查业务规则，不先加状态字段硬凑。

### 第 2 步：评审表关系、接口草案与代码边界

**功能：** 把业务规则转换成开发蓝图，此时还不执行建表。

**前提：** 操作和权限清单明确。

**新机制：** 一对多、多对多和历史版本解决不同问题。

**具体做什么：**

2. 明确经理多选放关系表，管理部门放人员角色关系，不用字符串拼 ID。
3. 明确 `business_key`、节点 key、visit、轮次、分支作用域及返回上下文的稳定标识。
4. 按第 7 章确定接口输入、输出、权限、错误结构和并发字段。
5. 确定新模块走内置注册，不再走插件发现。
6. 明确第一版条件语言为白名单字段+操作符+AND/OR 组合，不执行任意表达式。

**产出：** 可实施的模型和迁移清单、接口契约、引擎与项目适配协议。

**阅读起止：** 现有 `UserRolesModel`、`RoleDeptsModel`、`DeptModel.parent_id`；读到关系字段即停，先跳过关联加载优化。

**验收预期：** 能解释每张表为什么存在，以及 D 第二次进入为何不是第一次待办。

**第一排查点：** 发现一个字段同时表示“启用/审批状态/版本”时，先拆清语义。

### 第 3 步：先建项目三张表及其迁移

**功能：** 让项目资料可以可靠存储，先不加审批动作。

**前提：** 数据结构已评审，隔离验证环境已准备好。

**新机制：** ORM 模型描述目标结构，迁移负责把已有库升级到它。

2. 核对 `MappedBase`/Mixin 的审计、状态和索引，避免继承出不存在的索引列。
3. 编写或生成独立增量迁移，人工审核只涉及本功能；关联现有迁移链，不覆盖用户两份测试迁移。
4. 先在隔离空库验证模型创建，再在有历史表的数据副本验证升级。
5. 核对多选成员唯一约束、创建部门不可漂移、历史资料不可覆盖。
6. 不在共享库执行破坏性 downgrade；回退方案先在临时库验证。

**产出：** 项目模型和经审核的迁移；这一步才真正进入建表。

**阅读起止：** 拟新增 `ProjectModel` → `ProjectMemberModel` → `ProjectRevisionModel`；读到字段及约束停止，暂不读审批模型。

**操作与预期：** 在隔离库检查三张表、索引与迁移版本；现有用户、岗位数据不变。

**第一排查点：** 启动报映射/索引异常，先查 Mixin 和 `__table_args__`；不要先改数据库驱动。

### 第 4 步：完成项目草稿后端这条最小链路

**功能：** 创建人能创建、查详情、修改自己的草稿。

**前提：** 三张项目表可用。

**新机制：** Schema 校验输入，Service 决定业务是否允许，CRUD 执行明确查询。

**具体做什么：**

2. 实现创建、详情、更新、分页、草稿软删除；先从创建人范围开始，后续扩展管理范围但不能暂时裸查全部。
3. 更新同时替换两类成员关系并生成资料快照，整个操作在同一事务内。
4. 显式实现 `ProjectAccessPolicy`，不让当前 CRUD 旧权限意外改变新业务规则。
5. 创建接口只保存草稿，不创建审批实例。
6. 新接口仍挂登录、接口权限、统一响应与日志依赖。

**产出：** 第一批项目接口及接口级测试。

**阅读起止：** 拟新增 `create_project_controller` → `ProjectService.create_draft` → 创建模型/成员和 `flush` → 返回详情停止。再单独读 `update_draft`，不进入通用 CRUD 全部方法。

**操作与预期：** 接口创建“测试项目-001”，多选经理能读回；另一个普通用户不能通过换 ID 修改；`是否采购=false` 能保存。

**第一排查点：** 多选丢失先查成员表；详情查不到先查对象权限，不先给角色全部数据权限。

### 第 5 步：完成字典、最小选择目录、项目新建/详情页面

**功能：** 用户可以在真实页面创建项目，不再只看接口文档。

**前提：** 草稿接口可用；三个字典准备接入。

**新机制：** 字典 value 是稳定数据，label 是展示；页面显示和数据库校验不是同一层。

**具体做什么：**

1. 配置项目立项类型、项目类别、币种字典，使用明确前缀避免撞码。
2. 为已有环境增加幂等配置步骤，不只改种子 JSON；不重置现有菜单和字典表。
3. 接入受控的用户/部门选项接口。不要因选项目经理就授予“用户管理”全权限。
4. 实现独立 `create.vue`、`edit.vue`、`detail.vue`，抽出可复用表单与只读展示。
5. 九字段必填、日期校验、经理多选；页面校验只是体验，后端保留同样约束。
6. 注册页面路由和必要按钮权限；详情、编辑使用隐藏路由，不在菜单重复堆同级按钮。
7. 字典写入后验证数据库与前端缓存；现有 `RedisCURD.set` 返回失败值可能不抛异常，不能只看成功日志认定缓存刷新成功。

**产出：** 能操作的项目草稿页面及三类字典接入。

**阅读起止：** 新页面保存事件 → `ProjectAPI.create` → 第 4 步接口；看到返回项目 ID 停止。先跳过图形设计与任务页。

**操作与预期：** 页面保存后列表出现自己的项目，详情完整读回九字段；不出现所有人都能编辑的按钮。

**第一排查点：** 下拉空先查选项请求和字典 value；页面无法打开先查菜单 `component_path`，不要先重建数据库。

### 第 6 步：角色成员管理部门与项目查看范围

**功能：** 实现“B 是财务部负责人，因此能看财务部及其子部门单据”。

**前提：** 项目草稿可操作；现有用户角色关系可复用。

**新机制：** 用户所属部门、角色的数据范围、该角色成员管理部门是三种不同关系。

**具体做什么：**

1. 增加 `sys_user_role_managed_dept` 模型、迁移及成员级读写接口。
2. 在角色管理增加“成员/管理部门”入口，每位成员可以选择多个部门。
3. 校验操作者权限、成员确实属于角色、部门有效；移除成员需同步处理关系，不留下幽灵管理范围。
4. 负责人角色以稳定配置引用，不使用中文角色名称判断；普通角色拥有管理部门记录不自动冒充负责人。
5. 完成项目列表/普通详情权限：创建人 OR 负责人管理范围 OR 超级管理员；用 `creator_dept_id`，不沿创建人的当前部门判断。
6. 子部门范围计算包含自身、去重，并防止异常组织树回环；查询与分页总数使用同一条件。

**产出：** 成员管理部门配置页、项目对象权限和权限测试。

**阅读起止：** `ProjectService.page` → `ProjectAccessPolicy.list_condition` → 项目快照部门条件停止。先不读审批人的任务入口权限。

**操作与预期：** B 自己属于技术部，但管理财务部，能看财务部及其子部门项目；不能修改别人的项目；创建人调岗后归属不变。

**第一排查点：** 范围错误先对比管理部门关系和项目部门快照，不先改 `data_scope`。

### 第 7 步：业务角色目录与找人解析器

**功能：** 把“IT 项目经理”“创建部门负责人”转换成具体用户集合。

**前提：** 经理关系、部门管理范围已有数据。

**新机制：** 业务角色是规则入口，不是一个预先固定人员名单。

**具体做什么：**

1. 建业务角色目录及最小管理接口，白名单注册解析策略。
2. 实现项目适配器，暴露经理集合、创建部门快照及允许判断的业务字段。
3. 实现系统角色成员、两类经理、最近部门负责人解析器。
4. 向上找负责人时逐级查、遇到第一层有效人即停止；组织树异常明确失败。
5. 统一按用户 ID 去重，过滤停用/删除用户及停用/删除角色；返回命中来源说明。
6. 提供只读找人预览/诊断，不创建待办，不向无关普通用户暴露全员信息。

**产出：** 可测试的人员解析服务、业务角色配置、诊断结果。

**阅读起止：** `ResolverRegistry.resolve` → 某个规则解析器 → 返回用户集合停止；一次只跟 IT 经理或部门负责人一种来源。

**操作与预期：** 核算组没负责人、财务部有 B/C、集团有 D，结果只 B/C；多来源重复的 B 只出现一次。

**第一排查点：** 找错人先看规则编码、单据快照部门及来源解释，不先猜 SQLAlchemy 关联加载。

### 第 8 步：流程定义、版本保存和发布后端

**功能：** 保存并发布一套可以被执行的审批配置，还不做复杂画布。

**前提：** 人员规则可解析，流程表设计已审核。

**新机制：** 草稿可编辑，发布版不可变，已有实例引用具体版本。

**具体做什么：**

1. 增加流程模板、版本、节点、边、模块绑定模型和迁移。
2. 先用最简单串行配置验证保存、校验、发布、复制新版本、绑定模块。
3. 节点至少包含开始、审核、结束，以及后续分支类型的稳定结构。
4. 校验端点存在、节点 key 唯一、起止有效、审核角色合法、可达且能结束；不能发布孤岛或非法回环。
5. 发布时冻结规则配置、布局和内容摘要，提交时使用发布指针的一致快照。
6. 禁止删除/覆写被引用版本；发布和绑定操作记审计，配置权限与普通审批权限分离。

**产出：** 可发布的串行定义、不可变版本机制、项目模块绑定。

**阅读起止：** `DefinitionService.publish` → `GraphValidator.validate` → 冻结发布版本停止。暂时跳过并行作用域和返回机制。

**操作与预期：** v1 发布后改草稿不会影响 v1；已有实例引用的定义不可删除；无绑定时提交有明确提示。

**第一排查点：** 新旧配置混用先查实例 `definition_version_id`，不是只看模板名称。

### 第 9 步：实例、待办与串行提交闭环

**功能：** 首次跑通“保存项目 → 提交 → 第一人审批 → 第二人审批 → 项目通过”。

**前提：** 一条已发布并绑定的串行流程，找人服务可用。

**新机制：** 模板是规则，实例是这张单据正在运行的事实。

**具体做什么：**

1. 增加实例、轮次、执行 token、节点执行、任务、动作日志与幂等命令所需结构。
2. 实现提交全图预检查，首次绑定版本，原子创建运行数据。
3. 实现进入节点动态找人、生成本次固定名单、节点通过后的串行推进。
4. 实现审批命令的任务归属、资料版本及状态校验。
5. 实现待办/已办接口，以及任务专用的项目只读详情；不要给普通审批人项目全量详情权限。
6. 保持流程引擎通过适配器调用项目状态，不在核心引擎导入项目字段。

**产出：** 第一条真实审批闭环，任务级访问控制。

**阅读起止：** `ProjectService.submit` → `WorkflowCommandService.start` → `activate_node` → 写任务停止；随后另一次只读 `approve` → `advance`。

**操作与预期：** 创建人提交，指定人看到待办；未指定的人换 task_id 无权；最后通过后无残留待办；创建人就是审批人也必须手动点同意。

**第一排查点：** “项目审批中但没待办”先查实例、visit、任务及候选解析结果，不能只查项目状态列。

### 第 10 步：或签、会签、多人去重及并发保护

**功能：** 同一节点多人时，严格按配置决定何时结束。

**前提：** 串行闭环和独立任务身份已有。

**新机制：** 聚合的是本次节点的任务，不是整个单据所有历史同意票。

**具体做什么：**

1. 节点进入时冻结去重候选集合及审批模式。
2. 实现或签首个同意结束、会签全部同意结束、完成前一票否决。
3. 完成节点时关闭剩余任务；旧页面不能再投票。
4. 统一实例/节点/任务加锁顺序，用行锁、条件更新及唯一约束保障只推进一次。
5. 添加命令幂等键；同键不同请求内容拒绝，重复成功请求返回既有结果。
6. 审批时复核实际账号有效状态，不单凭登录缓存或名单快照放行。

**产出：** 多人模式和真实数据库并发验证用例。

**阅读起止：** `approve` → `complete_node_if_ready` → 判断本次 visit 的票数和状态即停。先跳过分支。

**操作与预期：** 同时点击两次不生成两批后继待办；或签关闭后不能再驳回；会签不因角色删掉一个人就悄悄降低人数。

**第一排查点：** 重复推进先查锁和唯一约束，不只在前端禁用按钮。

### 第 11 步：并行分支和全部汇合

**功能：** 技术、业务等审核同时进行，全部通过才继续。

**前提：** 节点多人模式稳定。

**新机制：** 并行需要多条执行路径，以及同一次分叉的汇合上下文。

**具体做什么：**

1. 增加并行作用域、分支 token 和汇合到达记录。
2. 发布校验分叉/汇合配对、路径完整、分支不能跳出自己的作用域。
3. 实现分叉一次激活多个分支、每分支一次到达、全部到齐只推进一次。
4. 支持与串行组合及结构正确的嵌套分支；使用父作用域区分嵌套，不强行假装任意图都合法。
5. 加入轮次隔离，旧轮次到达记录不能让新轮次提前汇合。

**产出：** 可运行的并行及嵌套作用域验证。

**阅读起止：** `activate_parallel_split` → 建 scope/token 停止；再读 `arrive_join` → 判断预期分支集合停止。

**操作与预期：** B 通过 C 未通过，不进入 D；最后两个分支并发完成，D 只有一次节点执行。

**第一排查点：** 提前汇合先查 round/scope/branch 身份，不先加固定审批人数判断。

### 第 12 步：条件分支、优先级与默认路线

**功能：** 根据项目字段自动选择且只选择一条路线。

**前提：** 发布结构、项目字段上下文和执行路径已有。

**新机制：** 条件配置是受限的数据结构，不是任意代码。

**具体做什么：**

1. 暴露字段目录和类型：是否采购、立项类型、类别、币种、业务部门、日期等；第一版不在画布开放密码等无关字段。
2. 实现类型匹配的等于、不等于、属于集合、日期比较、AND/OR 组合；不使用 `eval`、原始 SQL 或任意导入。
3. 明确分支优先级、唯一默认分支、默认最后兜底；发布时拒绝缺默认路线。
4. 到达网关时记录使用的资料版本、各条件结果和最终路线。
5. 条件合并只等待被选路径，不把未选路线当作并行待完成分支。

**产出：** 条件解释器、校验器及可追踪的路由决策。

**阅读起止：** `select_exclusive_branch` → `ConditionEvaluator.evaluate` → 命中第一条或默认路线停止。

**操作与预期：** 同时命中重点采购和普通采购时，只走高优先级；都不命中走默认；未选分支仍在提交预检范围，但不生成任务。

**第一排查点：** 走错路线先看字典 value、布尔类型、优先级和提交资料版本，不只看画布上的中文文字。

### 第 13 步：驳回重走与允许条件下撤回

**功能：** 先把“回起草、从头走”的较清晰路径做完整。

**前提：** 串行、并行、条件均有运行上下文。

**新机制：** 新一轮与旧历史共存，旧结果不能替代新审批。

**具体做什么：**

1. 实现驳回意见、暂停其他任务、返回起草与原版本重提。
2. 重新提交前再次全图找人校验；通过后新建轮次，旧任务取消。
3. 实现创建人的有限撤回，并和并发审批互斥判断。
4. 撤回再提交仍用原绑定版本，从入口走新一轮。
5. 实现删除退回草稿时终止实例、任务并保留历史。

**产出：** 重走、撤回、删除草稿的原子状态转换。

**阅读起止：** `reject_restart` → `suspend_instance` → 起草状态停止；再跟 `resubmit` → `start_new_round`。

**操作与预期：** 有人已经同意或驳回后，撤回失败；重走无选目标参数；旧分支的通过不会让新轮次提前通过。

**第一排查点：** 新一轮跳过节点先查是否复用了旧 visit、到达记录或返回链。

### 第 14 步：定点返回、嵌套返回和并行暂停恢复

**功能：** 实现本需求最复杂的“退过去处理，再回原环节”。

**前提：** 轮次、分支作用域、资料版本和重走机制稳定。

**新机制：** 返回链保存“处理完以后回哪里”，不只是把当前位置改成 B。

**具体做什么：**

1. 实现 `get_reject_targets`，从当前执行历史和作用域生成合法目标；审核节点以当前有效轮次实际经过路径为准，不从已失效的旧轮次随意取节点。
2. 禁止未来节点、跨并行分支、无效作用域节点及客户端伪造目标。
3. 保存返回上下文及暂停快照，激活目标处理链而不是一律把所有任务冻结。
4. D 退 B：B 新一次执行完成后直接 D，不经过 C，不重复推动原汇合。
5. D 退起草：任意修改后仍直接 D，不补走前置条件路线；重新提交照样检查全图人员。
6. 实现 D→B、B→起草的嵌套返回；等待最内层完成，再恢复外层。
7. 保留已通过的其他分支，恢复尚需处理的旧待办名单；对资料变化做版本提示和过期页面校验。
8. 返回链中选择重走时，终结旧链，使用新轮次；不能留下稍后自动跳回 D 的幽灵返回记录。

**产出：** 两种驳回全部行为、分支级/实例级暂停恢复测试。

**阅读起止：** `reject_targeted` → `ReturnService.push_context` → 激活目标即停；下一次读 `complete_return_target` → 恢复原节点。先跳过日志序列化和画布高亮。

**操作与预期：** 使用 A/B/C/D、并行已过/未过、嵌套三类场景逐一验证。页面可见“正在补审 B，完成后返回 D”。

**第一排查点：** 跳转错误先查 return_context 父链和 scope；另一分支仍能审批先查暂停态校验，不只隐藏按钮。

### 第 15 步：运行缺人、人员失效诊断与受控恢复

**功能：** 人员配置变化不会使流程悄悄消失或自动通过。

**前提：** 进入节点会动态找人，且审批动作是原子命令。

**新机制：** “业务上阻塞”可以是一种合法持久状态，不等于系统崩溃。

**具体做什么：**

1. 区分提交预检失败、进入节点无人、固定名单成员失效、配置引用失效、数据库故障。
2. 阻塞记录保存节点、规则来源、查找部门层级和失败原因，但不输出秘密信息。
3. 为可恢复的“激活节点无人”提供授权重试接口，补齐配置后只激活一次。
4. 当前会签名单成员失效时，不自动替换为新角色成员；给出可解释的阻塞状态和处理提示。需要修改固定名单的能力属于另行受控扩展，不在本版暗加转交。
5. 恢复命令与审批命令共用实例锁、幂等约束和审计。
6. 页面显示“上一节点已审批通过，下一节点缺人阻塞”，不误报成审批失败要求重复投票。

**产出：** 可定位的异常页面/接口与安全恢复路径。

**阅读起止：** `activate_node` → 空候选诊断 → `block_instance` 停止；再读 `retry_blocked_activation`，不扩展到超时调度。

**操作与预期：** 提交后删除尚未激活角色的成员，进入该节点阻塞；补齐后重试，旧审批不丢、不重复推进。

**第一排查点：** 状态未保存先看是否错误抛异常让整次审批事务回滚。

### 第 16 步：可视化流程设计器与系统管理配置页面

**功能：** 管理员不用手写 JSON，即可画图、选角色、设条件、发布并绑定项目。

**前提：** 后端定义、发布校验及运行语义已验证，避免画布先行掩盖引擎缺失。

**新机制：** 画布是配置入口，后端校验才是执行规则的最终约束。

**具体做什么：**

1. 阅读仓库当时的 UI/品牌规范及现有公共组件，沿用本项目，不套用别的仓库页面规范。
2. 基于现有 Vue Flow 依赖新建审批设计器，参考交互但不修改文件传输流程业务。
3. 支持开始、审核、结束、条件分支/合并、并行分叉/汇合；显示结构校验错误。
4. 节点面板支持系统角色/业务角色多选、或签/会签；负责人规则显示固定创建部门来源与最近上查策略。
5. 条件面板支持字段、操作符、值、组合、优先级与默认路线，不提供任意脚本编辑器。
6. 保存草稿、校验、预览、发布、复制版本、切换已发布版本查看、模块绑定分别呈现。
7. 发布版只读；运行实例展示自己绑定的版本，不用当前最新图覆盖历史。
8. 注册系统管理里的“审批流程配置”“业务角色”及对应权限；流程编辑器使用独立页或适合项目规范的全屏界面。

**产出：** 满足最初需求的可视化配置模块。

**阅读起止：** 新 `designer.vue` 的保存事件 → `DefinitionAPI.saveDraft` → 第 8 步保存接口停止。拖拽库内部、图布局算法先跳过。

**操作与预期：** 管理员可从空白图配置“开始→经理→部门负责人→结束”，再加入条件和并行；非法图无法发布。

**第一排查点：** 显示和执行不一致先核对节点/边事实与布局数据，不能只调画布颜色。

### 第 17 步：项目审批页、待办/已办与版本化审批轨迹

**功能：** 让创建人和审批人看得懂“现在在哪、该谁处理、之前批准了哪份资料”。

**前提：** 引擎完整、任务权限和历史版本已落地。

**新机制：** 查看权限来自具体任务；操作权限来自具体待办状态，两者分开。

**具体做什么：**

1. 完成项目列表状态、当前活跃节点集合及创建/提交入口；并行时显示多个活跃节点，不强行只显示一个。
2. 我的待办进入独立审批页，资料只读；同意、驳回、模式、合法目标、意见按能力显示。
3. 已办只读；或签被其他人结束的任务显示“已关闭”，不冒充本人同意。
4. 详情显示实例版本、轮次、资料版本、审批轨迹、并行/返回/阻塞状态。
5. 选择历史审批记录时展示其实际资料快照；旧分支保留通过时明确标注“审批于资料 vN”。
6. 页面提交携带 task_id、expected_revision、expected_version 和幂等键；过期后提示刷新，不偷偷换版本代批。
7. 按钮依据后端返回的 `allowed_actions` 显示，但后端仍重新校验，不能把按钮隐藏当作权限实现。

**产出：** 用户可以完整操作的项目与审批工作台。

**阅读起止：** `approval.vue` 同意事件 → `TaskAPI.approve` → `WorkflowCommandService.approve` → 返回 allowed_actions/状态停止；先跳过通用 UI 库。

**操作与预期：** 审批人能从待办打开不在自己项目列表里的项目；换 task_id 越权失败；返回后旧页面不能批准新资料。

**第一排查点：** 有待办打不开先看任务专用详情权限和隐藏路由是否授予，不先开放项目全量查看。

### 第 18 步：联调、异常与并发验收

**功能：** 证明不只是“正常点一次可以用”，而是边界也符合确认规则。

**前提：** 全功能能在隔离环境运行。

**新机制：** 静态阅读、单元测试、接口测试和真实数据库并发测试证明的范围不同。

**具体做什么：**

1. 按第 8 章矩阵逐项执行并记录结果，覆盖权限、分支、版本、重走、返回、人员变更。
2. 纯条件/图校验/返回目标计算做单元测试；持久化与任务访问做接口测试。
3. 并发同意/驳回、重复提交、汇合去重、事务回滚在与目标部署同类型数据库的隔离库测试。
4. 不用 SQLite 单写连接或 Mock 的通过结果宣称 MySQL 行锁和并发已经验证。
5. 运行现有回归测试前检查 conftest。当前测试会建立临时 SQLite 并调用初始化；不能把测试布局可能写迁移文件视为绝无副作用。
6. 前后对比 Git 状态和迁移目录；所有自动产生的文件都要先识别来源，不一键清理。
7. 前端执行类型检查、定向测试及构建；现有 lint 命令含自动修复，不在脏工作区对全仓无差别执行。

**产出：** 验收报告，明确哪些已运行、在哪个环境通过，哪些仅静态推断或尚未验证。

**阅读范围：** 只读失败场景的 controller/service/断言，不要求先学完测试框架内部。

**异常教学方式：** 先描述实验并给你预测机会；你可以直接说“继续”或不预测，再观察结果、解释原因、给第一排查点。

### 第 19 步：发布准备与交付

**功能：** 从开发环境走到可维护的实际使用环境，不靠临时手工改库维持。

**前提：** 验收通过，目标环境和发布窗口获得授权。

**新机制：** 代码部署、数据库升级、业务配置和授权是不同的发布事项。

**具体做什么：**

1. 审核迁移链、数据备份、发布顺序、兼容性与回退策略。
2. 区分空库自举和已有库升级，验证增量配置可重复执行而不覆盖现有数据。
3. 配置真实字典、负责人角色/成员管理部门、业务角色、流程图、模块绑定。
4. 授予创建、配置、发布、审批工作台、阻塞恢复等最小权限；普通审批入口不能要求用户拥有系统配置权限。
5. 先发布应用和结构，再补必要配置，再启用模块提交；无发布流程时接口明确拒绝，而不是乱走默认。
6. 用专门验收账号做一条串行、一条并行/条件、一条退回重提的冒烟验证。
7. 交付操作说明、权限表、缺人排查指南、备份与升级记录。
8. 不因“写计划”或“本地开发”就直接操作生产、自动合并用户改动或创建外部 PR。

**产出：** 可发布版本、验收记录、管理员配置手册、用户操作手册。

**验收预期：** 新环境能配置并运行；已有环境升级不丢用户数据；重启服务后审批进度完整。

**第一排查点：** 上线后无菜单先查增量菜单配置和用户会话/授权，不重新初始化全库。

## 第 7 章：接口契约草案

以下是拟新增业务路径。外部 `/api/v1`、网关或前端代理前缀按现有项目实际配置接入，不能直接假定完整请求地址。具体请求/响应 Schema 在第 2 步定稿。

### 7.1 项目接口

| 方法与路径 | 功能 | 核心对象权限 |
| --- | --- | --- |
| `GET /business/project/list` | 分页和筛选 | 创建人/管理部门及子部门/超管；总数同范围 |
| `GET /business/project/detail/{id}` | 普通项目详情 | 同列表范围，不给任务关联项目自动全局放行 |
| `POST /business/project/create` | 创建草稿 | 当前用户创建，后端记录身份和部门 |
| `PUT /business/project/update/{id}` | 修改草稿 | 仅创建人、仅可编辑起草、版本未过期 |
| `DELETE /business/project/delete/{id}` | 软删除草稿 | 仅创建人，并终止关联挂起运行数据 |
| `POST /business/project/{id}/precheck` | 只读提交预检查 | 仅创建人；不绑定版本、不创建待办 |
| `POST /business/project/{id}/submit` | 首次或再次提交 | 仅创建人；必须重新执行服务端预检查 |
| `POST /business/project/{id}/withdraw` | 有限撤回 | 仅创建人、尚无手动审批操作 |
| `GET /business/project/options/users` | 最小人员选项 | 已授权项目发起用户，最小返回字段和分页 |
| `GET /business/project/options/depts` | 业务部门选项 | 已授权项目发起用户，不授予部门管理写权限 |

预检查与正式提交有时间差，因此预检查成功不构成免检凭证。提交失败尽量一次返回所有缺人节点，避免用户修一个再报下一个。

### 7.2 任务与运行接口

| 方法与路径 | 功能 | 校验重点 |
| --- | --- | --- |
| `GET /workflow/task/todo` | 我的待办 | assignee 为当前用户；暂停/阻塞明确展示而不可操作 |
| `GET /workflow/task/done` | 我的已办 | 本人真实参与或按关闭类别展示，不伪造本人审批行为 |
| `GET /workflow/task/{task_id}/detail` | 任务专用详情、资料、轨迹 | 先校验任务归属，再经适配器读单据，不依赖普通列表权限 |
| `GET /workflow/task/{task_id}/reject-targets` | 当前合法退回目标 | 当前待办与执行上下文，不能直接列全图节点 |
| `POST /workflow/task/{task_id}/approve` | 同意 | 本人、活跃、资料版本、任务版本、幂等键 |
| `POST /workflow/task/{task_id}/reject` | 两种驳回 | 模式、意见；重走无目标；定点目标服务端复核 |
| `POST /workflow/instance/{id}/retry-activation` | 缺人节点受控重试 | 专门恢复权限、当前确为可恢复的激活阻塞 |

任务只读详情可用于本人关闭/暂停的任务查看状态，但绝不能据此继续审批；已软删项目显示终止信息与允许保留的历史，不重新开放编辑。

### 7.3 配置接口

| 路径组 | 内容 |
| --- | --- |
| `/system/workflow/...` | 模板列表、草稿版本保存、校验、发布、复制版本、只读版本详情 |
| `/system/workflow/binding/...` | 查询/设置项目模块默认流程 |
| `/system/business-role/...` | 业务角色目录、白名单策略及参数配置 |
| `/system/role/{role_id}/members/...` | 查询现有角色成员及其管理部门；不重写现有用户角色授权机制 |
| `/system/role/{role_id}/members/{user_id}/managed-depts` | 读取/设置这个角色成员的管理部门 |

权限编码沿用仓库 `module_xxx:resource:action` 风格，为项目查询/详情/创建/修改/提交/删除/撤回、任务入口/处理、流程配置/发布、管理部门配置、阻塞恢复分别定义。接口权限只是第一层，所有写操作还要校验具体对象和状态。

### 7.4 提交与审批响应至少说明什么

- 当前项目/实例状态、流程版本、资料版本。
- 当前活跃节点集合，而不只是一个节点名。
- 这次操作是否已经成功；是否出现后续阻塞及其原因。
- 当前用户允许执行的动作。
- 错误定位：字段、节点 key、节点名称、人员来源和缺失原因。
- 审批请求必须提交预期资料版本；不能只传一个项目 ID 和“同意”。

错误示例：`部门负责人审核：创建部门“核算组”及上级均未找到该负责人角色的有效成员。项目仍为起草，未创建审批任务。`

运行阻塞示例：`本次技术审核已通过；进入“部门负责人审核”时未找到有效审批人，流程已暂停，等待管理员补齐配置后恢复。`

## 第 9 章：验收方式、实施节奏与交付约定

### 9.1 不把“写完代码”当成“已验证”

每步交付明确标注：

1. **静态推断**：从源码读到的调用和约束。
2. **隔离测试证据**：具体测试、数据库类型、通过结果。
3. **真实页面/接口证据**：操作账号类型、请求与可见结果，不记录密码/Token。
4. **尚未验证**：缺环境或数据时直说，不以预期替代事实。

本次文档交付只属于第 1 类及设计产出，没有宣称业务功能已经运行。

### 9.2 建议的开发里程碑

| 里程碑 | 对应步骤 | 用户可见成果 |
| --- | --- | --- |
| M0 设计就绪 | 0～2 | 规则、数据、接口和验证环境清楚 |
| M1 项目草稿可用 | 3～5 | 可以新增、编辑、查看九字段项目 |
| M2 组织配置与找人可用 | 6～7 | 可配置每人管理部门，正确找出审批人 |
| M3 串行审批可用 | 8～10 | 一条真实串行流程、待办、或签/会签 |
| M4 完整流转可用 | 11～15 | 并行、条件、两种驳回、嵌套返回、阻塞恢复 |
| M5 完整页面可用 | 16～17 | 可视化配置、项目审批页、待办/已办与轨迹 |
| M6 可交付 | 18～19 | 验收证据、迁移及配置、操作/维护说明 |

不把这套完整引擎估成“加一张项目表和几个接口”。最有风险的是返回上下文、并行暂停/汇合、历史资料与权限一致性；这些应先在后端小样例验证，再做复杂画布。

不在不了解目标环境和验收投入前承诺固定天数。每个里程碑完成后可以停下来观察；停下学习不代表留下可被其他用户误用的半成品入口，未完成能力不发布或不启用。

### 9.3 后续每次带你实现的固定方式

每次开头先说：

- 这次完成哪个业务功能，最终页面/接口会有什么变化。
- 依赖哪些已经完成的东西。
- 只引入一个主要新机制，例如关系表、资料版本、节点执行或返回链。

然后按一条请求路径讲：从哪个函数进入、每一步负责什么、读到哪里停、哪些辅助函数先跳过。新函数名与本文建议不同会明确说明，不让你去寻找不存在的实现。

最后给你：已改文件、操作步骤、预期结果、实际运行证据与未验证部分、结果不符时第一个该查的位置。遇到异常先给预测机会，再展示和解释；预测与扩展都可以跳过。

### 9.4 当前完成状态与下一步

- 已完成：主要业务需求访谈、当前源码静态核对、本实施计划。
- 未开始：业务模型、接口、页面、迁移和基础设施改动。
- 下一步：按第 0～2 步审核设计与环境，随后先做第 3～5 步的项目草稿最小链路。

实施中若发现必须扩大权限、改变已确认业务、修改基础设施或处理无法安全绕过的用户改动，会先说明影响并征求方向，不以“为了跑通”为由擅自处理。
