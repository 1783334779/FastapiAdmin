# 菜单管理学习路线

依据：2026-10-30 当前工作区源码。本文只规划阅读与观察，不修改菜单、角色、登录会话、业务代码或基础设施。

## 一、先确定学习目标

学完应能独立解释：

1. 系统有哪些菜单资源，目录、页面、按钮权限为什么放在同一张表。
2. 普通用户通过哪些关联获得菜单和权限。
3. 菜单管理页的菜单树，与当前用户侧栏菜单分别来自哪个接口。
4. 数据库中的路由、组件路径怎样变成前端可访问的页面。
5. 隐藏菜单、隐藏按钮、拒绝后端接口为什么是三件事。
6. 新增、禁用、授权之后，为什么当前页面或已有登录会话不一定立即同步。

每次讲完一章，每章只跟一个操作。固定结构为：功能 → 已有前提 → 一个新机制 → 按调用顺序阅读 → 操作/预期/第一排查点。遇到异常先预测，再观察和解释；扩展不作为继续条件。无需亲自写代码。

## 二、核心表：先只记这五张

| 表 | 一行代表什么 | 重点字段 |
| --- | --- | --- |
| `sys_menu` | 一项菜单资源，可能是目录、页面、按钮权限或外链 | `id`、`parent_id`、`type`、`permission`、`route_path`、`component_path`、`hidden`、`status`、`scope` |
| `sys_role` | 一个系统角色 | `id`、`code`、`status` |
| `sys_role_menus` | 某个角色拥有某项菜单资源 | `role_id`、`menu_id`，联合主键 |
| `sys_user` | 一个用户 | `id`、`is_superuser`、`status` |
| `sys_user_roles` | 某个用户拥有某个角色 | `user_id`、`role_id`，联合主键 |

普通用户的授权关系：用户 → 用户角色关联 → 角色 → 角色菜单关联 → 菜单资源。超级管理员有单独分支，第一轮学习不从超级管理员推断普通用户行为。

树结构不靠额外的“菜单树表”：`sys_menu.parent_id` 引用同表的父记录，再由后端组织 `children`。

`sys_dept`、`sys_role_depts`、`sys_user_positions` 不属于本轮菜单授权主线。它们涉及数据权限或其他业务，先跳过。Redis 会话也参与运行时权限，但不是第六张关系表。

## 三、两条入口必须分开

- 菜单管理页面：`GET /system/menu/tree`，维护菜单资源的查询入口。
- 登录后的个人菜单：`GET /system/user/current/info`，从响应的 `menus` 进入前端菜单与路由处理。

接口地址省略统一 API 前缀；浏览器 Network 的完整地址以本地配置为准。

当前前端 `.env` 配置 `VITE_ACCESS_MODE=mixed`，即后端菜单与前端内置路由来源合并；menu store 还会补充壳层菜单。因此不能假设侧栏每一项都严格对应一条 `sys_menu` 记录。

## 四、章节安排

### 第 1 章：菜单管理页怎样查询出一棵树

功能：看懂系统已配置的资源，以及一张表如何表示多级目录。已有前提：知道表中的一行和 HTTP 响应的关系。新机制：`parent_id` 自关联与树形组装。

阅读路线：

1. 从 `backend/app/modules/system/menu/controller.py:get_menu_tree_controller` 开始。
2. 进入 `MenuService.tree`，确认它先查询平铺记录，再转换为字典。
3. 打开 `backend/app/utils/common_util.py:traversal_to_tree`，看记录怎样放进父节点的 `children`。
4. 回到 Controller，看到返回树即停。需要认字段时才对照 `menu/model.py`。

暂跳：通用 CRUD 的条件构造和 SQLAlchemy 加载策略；登录；角色；前端动态路由。

操作：有权限时打开“系统管理 → 菜单管理”，只查询已有数据，在 Network 找 `/system/menu/tree`。

预期：响应包含 `parent_id`、`type`、路由字段和 `children`；按钮权限也可能作为树节点出现，但不是侧栏页面。

第一排查点：响应无记录先查搜索参数、`scope` 和权限；层级异常查 `parent_id`。当前 `traversal_to_tree` 在父记录不在输入集合时可能把子项放到根层，不要把它理解为所有缺父项都自动丢弃。

### 第 2 章：新增和修改菜单，到底配置了什么

功能：区分目录、页面、按钮权限、外链，以及路由地址和组件路径。已有前提：第 1 章。新机制：不同资源类型适用不同字段和父子规则。

阅读路线：从 `menu/controller.py:create_obj_controller` → `MenuCreateSchema` → `core/validator.py:menu_request_validator` → `MenuService.create` → `_validate_parent_child_type/_validate_parent_child_scope` → `MenuCRUD.create`。看到新增响应即停。修改另读 `update_obj_controller` → `MenuService.update`，不与新增同时跳读。

第一轮重点：`type`、`parent_id`、`route_name`、`route_path`、`component_path`、`permission`、`hidden`、`status`、`scope`。目录可包含目录/页面/外链，页面下当前只允许按钮；新增菜单配置不会生成对应 Vue 文件。

暂跳：图标、角标、iframe、标签固定、缓存、组件框架内部。

操作：只打开已有菜单详情或新增表单查看字段，不必保存。需要实验时另建独立学习资源，不改核心系统菜单。

预期：页面菜单的 `component_path` 指向已有前端组件；按钮资源保存权限字符串而不是页面。

第一排查点：保存失败先读字段校验与父子类型约束；菜单配置存在但页面打不开，留到第 5 章排查组件映射。

### 第 3 章：角色授权如何把菜单分配给用户

功能：区分“资源已经创建”和“普通用户已经获得资源”。已有前提：两张关联表的作用。新机制：多对多关联及关系替换。

阅读路线：角色授权接口 `role/controller.py:set_role_permission_controller` → `RoleService.set_permission` → `_set_role_menus` → `RoleCRUD.set_role_menus_crud`。读到 `obj.menus.clear()/extend()` 和 `flush()` 即停，理解 ORM 写入 `sys_role_menus`。

用户角色关联另看 `UserService._set_user_roles` → `UserCRUD.set_user_roles`，确认它写的是 `sys_user_roles`，不是 `sys_role_menus`。

暂跳：角色的数据范围、管理部门、岗位、完整用户 CRUD。

操作：查看已有普通学习用户的角色，以及这些角色授权的菜单树；不要求更改真实账号权限。

预期：角色勾选菜单 ID；用户关联角色 ID；多角色的资源可以汇总。按钮权限也是 `sys_menu` 的 type=3 记录，并非另一张“按钮表”。

第一排查点：用户没菜单时先沿两张关联表检查，不要仅因为 `sys_menu` 存在就认为用户已授权。不要用超级管理员的显示结果替代普通用户验收。

### 第 4 章：登录后，后端怎样给出当前用户的菜单与权限

功能：跟踪菜单 ID 和权限字符串的来源。已有前提：第 3 章的关联关系。新机制：登录会话中的权限快照。

阅读路线分成两个连续观察段，不从 JWT 加密算法开始：

1. `auth/service.py:LoginService._collect_permissions` → `create_token` 中收集及写会话的位置 → `_build_session_dict`。看到 `menu_ids`、`permissions` 放入 Redis 会话即停。
2. `user/controller.py:get_current_user_info_controller` → `UserService.current_info` → `_load_menus` → 树形返回。需要解释 `auth.menu_ids` 来源时，再看 `dependencies.py:_authenticate` 读取 Redis 的相关行。

暂跳：密码哈希、验证码、OAuth、Token 续期算法、Redis 客户端封装。

操作：观察普通学习账号正常登录后的 `/system/user/current/info` 响应，不展示或复制真实 Token、会话值。

预期：登录时从启用角色与菜单汇总权限；普通用户菜单加载使用 `auth.menu_ids`；超级管理员走另一条加载路径；Web 菜单限定 `scope=web`。

第一排查点：授权数据库已改但旧登录结果不符，先区分数据库、Redis 会话和前端 store。刷新菜单接口不等于重新计算登录权限；重新登录是可选观察方式，不预设即时热更新已经实现。

### 第 5 章：后端菜单怎样变成侧栏和可访问页面

功能：跟踪一个已返回的页面菜单，直到注册成 Vue Router 路由。已有前提：第 4 章的 `menus` 响应。新机制：资源数据到页面组件的映射。

阅读路线：`user.store.ts:getUserInfo/setRoute` → `MenuProcessor.getMenuList/processBackendMenu` → `mapMenuNode` → `guards.ts:handleDynamicRoutes` 的 store 写入和注册调用 → `RouteRegistry.register` → `RouteTransformer.transform` → `ComponentLoader.load`。看到组件路径映射和 `router.addRoute` 即停。

侧栏显示另看 `menu.store.ts:setMenuList` 与 `FaSidebarSubmenu.vue:filterRoutes`；先跟一个普通页面，不同时追三个布局。

暂跳：前端模式的全部分支、iframe、复杂 Layout、KeepAlive、标签页、个人审批静态路由的特殊放行规则。

操作：在当前用户响应中找一项已有的普通页面菜单，对照其 `route_path` 和 `component_path`，再打开该页面。

预期：父子路径按规则拼接；组件路径映射到 `src/views` 中真实 Vue 文件；type=3 按钮资源不会变成侧栏页面；`hidden` 影响显示，不能当作后端拒绝访问的依据。

第一排查点：先看后端是否返回 → store 是否收到 → 是否被隐藏/空目录过滤 → 路由是否注册 → 组件路径是否匹配。mixed 模式与壳层补全需单独辨认来源。

### 第 6 章：一个权限字符串，怎样控制按钮与后端接口

功能：理解前端展示控制与后端安全校验的边界。已有前提：知道 `sys_menu.permission` 和会话权限。新机制：两端使用一致的权限标识，但分别执行检查。

阅读路线：选择现有按钮的 `v-hasPerm` → `directives/permission/index.ts:mounted` → `useAuth().hasAuth` → `utils/checkPerm.ts:checkPerm`；再看对应后端 Controller 的 `AuthPermission([...])` → `dependencies.py:AuthPermission.__call__`。读到允许或抛出异常即停。

同时对照 `user.store.ts:setPermissions`，看前端权限集合从菜单及用户角色资源中汇总，不能误认为它与 Redis 权限必定实时相同。

暂跳：通配符的所有兼容情况、前端短权限标识、请求拦截器全部错误处理。

操作：优先查看已有学习账号的按钮差异与请求结果，不要求构造越权请求或修改真实角色。

预期：前端无权限时隐藏已实现的业务按钮；后端无权限时仍拒绝请求；仅新增按钮权限配置不会自动生成页面按钮。前后端权限数组当前都是任一匹配语义，不自动表示同时满足全部权限。

第一排查点：按钮不见先看前端 `prems` 与指令；按钮可点但 403 则看后端会话权限和接口要求。前端检查不是后端安全边界。

### 第 7 章：新增、隐藏、禁用、删除和授权变更后怎样排查

功能：把前六章组成一条问题定位路线。已有前提：菜单、授权、会话、前端路由与按钮的来源。新机制：不同层的状态需要分别更新。

阅读路线：`MenuService.set_available/delete` → 前端菜单页保存后的 `refreshPermissions` 调用 → `user.store.ts:refreshPermissions` → `router/refresh.ts:refreshMenuAndRoutes`，确认谁调用谁，而不是看到函数名就断言每次都自动重建路由。

暂跳：在真实环境批量停用、删除或修改角色；这些操作仅在独立学习数据或隔离环境观察。

预期：`hidden` 不是停用；停用和删除可能连带下级；重新取当前用户菜单、重建动态路由、重算 Redis 登录权限是三个不同步骤。

第一排查点顺序：菜单记录及祖先 → 用户/角色关联 → 当前会话 menu_ids/permissions → current/info 响应 → 前端 routeList/menuList/prems → 动态路由/侧栏/按钮。

异常先预测的例子：普通用户登录后才给角色新增一个菜单，只刷新浏览器是否一定获得？先判断，再对照会话快照与当前用户加载逻辑；不要预设刷新就重算角色授权。

## 五、必须按当前实现辨认的边界

1. `MenuService` 类注释写“查询操作租户可见，写操作仅超级管理员可操作”，但当前 Controller 的写入口按 `AuthPermission` 检查相应业务权限，Service/CRUD 没有据此注释自动增加租户或仅超管判断。学习时以实际调用和条件为准；本文不修改这些行为。
2. 菜单管理树与个人侧栏菜单不是同一个接口，也不是同一份用途的数据。
3. `scope` 在当前实现指 Web/App 菜单范围，不是部门数据范围，也不是角色授权关系。
4. 有菜单不代表按钮权限自动齐全；有按钮权限配置也不会凭空生成 Vue 按钮。
5. 删除方式必须检查基类条件：`CRUDBase` 只有检测到 `is_deleted/deleted_time/deleted_id` 三项时才走软删除；当前 `MenuModel` 没有 `deleted_id`，不能仅因它有 `is_deleted` 就认定删除一定是软删除。删除观察不得使用真实系统菜单。

## 六、建议的第一步

只做第 1 章：打开菜单管理页，找到 `/system/menu/tree`，从 `get_menu_tree_controller` 顺着 `MenuService.tree` 读到返回 `children` 为止。

登录、角色授权、动态路由、按钮权限都先不进入。之后按上述章节顺序继续，不在一章里跳完所有文件。

证据范围：本路线来自当前源码只读核对，未实际登录、变更权限、调用写接口或执行测试；观察结果均列为预期，不当作实际运行证据。没有新增测试文件。
