# FastapiAdmin：从手动部署到 GitHub 自动发布

这份教程面向后端新手，按当前仓库源码讲解。目标不是先背 Docker 命令，而是理解：代码如何变成服务器上运行的服务，以及如何把已经验证过的部署步骤交给 GitHub 执行。

本次只新增这份文档，没有连接服务器、安装软件、修改部署配置或启用自动发布。文中的配置、脚本和 Actions 都是供你学习后手动创建的模板，不是已经生效的文件。

## 先说明适用范围

- 示例环境：**新建的、没有其他业务的 Ubuntu 24.04 x86_64 学习服务器**，使用 MySQL、Redis、Docker Compose，以及一个已经解析到服务器的域名。
- 示例分支：`master`，因为当前本地分支是 master；不是说只能使用它。
- 示例域名：`learn.example.com`，必须换成自己的域名。
- 固定学习目录：`/opt/fastapiadmin-study`。所有示例都围绕这个目录，不要随手改成其他项目正在使用的目录。
- Windows、ARM、已有宝塔/1Panel、已有 MySQL、已有网站、没有域名或证书时：先学习概念，**不要直接执行启动部分**，需要另行适配。当前 Compose 带固定容器名称、端口和 amd64 平台，不能直接往共享服务器套用。
- 自动部署只是执行操作的方式，不会自动解决业务兼容性、数据库迁移和数据丢失问题。

建议分三次学习：第一至五章完成一次手动上线；第六、七章理解更新和回滚；第八、九章再开启自动化。扩展内容可以跳过，不作为继续条件。

## 第一章：部署究竟在做什么

### 1.1 先看整体功能

本地开发时，你启动 Vite 和 Python；正式部署后，用户不应该访问开发服务器。

| 部分 | 部署后由谁运行 | 负责什么 |
| --- | --- | --- |
| Vue 前端 | Nginx 提供构建后的 `dist` 文件 | 把页面、JS、CSS 发给浏览器 |
| FastAPI 后端 | Python 后端容器 | 登录、项目、审批、邮件等接口 |
| MySQL | 数据库容器 | 保存用户、项目、流程等业务数据 |
| Redis | Redis 容器 | 保存登录会话、缓存、邮件测试冷却等 |
| Nginx | Nginx 容器 | HTTPS、静态页面、转发 `/api/v1` 请求 |
| Docker Compose | 服务器上的编排工具 | 将上述服务按配置启动并连接起来 |
| GitHub Actions | GitHub 的执行环境 | 收到推送后做检查，并触发服务器部署 |

一个请求的去向：浏览器访问 `https://你的域名/web/` 获得前端；前端请求同一域名下的 `/api/v1/...`，Nginx 再把它转给后端。

### 1.2 只引入一个新机制：镜像与容器

**镜像**是程序和运行环境的打包结果；**容器**是镜像启动后的运行实例。更新程序通常是构建新镜像、重建应用容器，而不是进入旧容器手改代码。

业务数据不能只存在容器里。容器可以换，数据库、上传文件、私有附件必须留在持久化目录中。

### 1.3 从哪些文件开始看

按顺序读，不需要同时打开全部文件：

1. `docker/backend/Dockerfile`：从 `FROM python:3.12-slim` 读到 `CMD` 停。先理解安装依赖、复制后端、非 root 运行和启动命令；LABEL 等元数据暂时跳过。
2. `docker/docker-compose.yaml`：先看 backend 的 `build`、`environment`、`volumes`；再看 nginx；最后看 mysql、redis。资源限制、日志轮转可暂时跳过。
3. `docker/nginx/nginx.conf`：先看 `/web` 和 `/api/v1` 两个 location，理解页面和接口如何分流。gzip、缓存参数先跳过。
4. `.github/workflows/backend-ci.yml` 和 `frontend-ci.yml`：看 `on`、`jobs`、`steps`，暂不追进每个测试文件。

### 1.4 当前源码与旧说明不一致的地方

下面都来自源码静态核对，不代表已经在你的服务器运行过：

- `docker/README.md` 描述部署脚本会“更新代码”，但当前 `deploy.sh` 明确不执行 git 拉取，也没有实现文档里的前端构建选项；它主要构建后端并启动服务。
- `deploy.sh` 的正常流程没有先停止全部服务，但其中断信号处理会调用停止服务，且会清理共享 Docker 构建缓存。不要直接拿它作为自动发布脚本。
- `deploy-artifacts.sh` 有既定服务器和目录参数，不能未经核对就执行。
- Nginx 注释说根站点和 app “已禁用”，但对应 location 仍在配置中。主项目学习入口先用 `/web/`，不要把根路径打不开误认为后台没启动。
- 文档中出现的 `NGINX_SERVER_NAME` 不会自动替换当前 Nginx 配置里的域名；Compose 的环境变量不等于 Nginx 模板替换。
- 后端默认 `DEBUG=True`；即使选择 prod，也必须显式配置 `DEBUG=False`，不能把 prod 理解为“自动关闭所有开发功能”。

## 第二章：检查学习服务器，不急着安装和启动

### 2.1 在服务器终端执行的只读检查

```bash
uname -m
lsb_release -a
free -h
df -h
ss -lnt
ip route
docker version
docker compose version
git --version
node --version
pnpm --version
```

**预期**：系统和架构符合本教程；磁盘有足够空间保留代码、镜像、数据库和备份；80、443 端口未被其他业务占用。后续在服务器构建前端，还需要 Node.js 22 的受维护补丁版本和 pnpm 10，与当前锁文件和 CI 使用方式保持一致；不要直接安装不受控的 pnpm latest。

这不是强制硬件最低配置。小内存机器在构建时可能耗尽内存；可以改为在 CI 构建后交付产物，而不是盲目增加重试次数。

**第一排查点**：命令不存在先确认是否未安装；Docker 权限不足不等于 Docker 没安装；已有网站或容器时停止套用本教程。

安装按官方系统文档进行，不在未知服务器上执行通用的“一键安装＋卸载旧环境”脚本：[Docker Ubuntu 安装](https://docs.docker.com/engine/install/ubuntu/)、[Node.js 下载](https://nodejs.org/en/download)、[pnpm 安装](https://pnpm.io/installation)。安装时保留现有 SSH 登录方式，不要因调整防火墙把自己锁在外面。

### 2.2 账号与网络

- 创建专用部署账号，例如 `deployer`，不要直接把 root 私钥交给 GitHub。
- 该账号需要对学习目录有写权限，并具备执行本项目 Docker 操作的权限。**加入 docker 组通常等价于拥有很高的宿主机控制能力**，不能把它当成普通低权限账号；学习环境要与其他重要业务隔离。
- 公网按需开放 80/443；SSH 限制来源，优先使用密钥。不要把 3306、6379、8001 直接向公网开放。
- Docker 发布端口可能绕过部分 UFW 规则，既要检查云安全组，也要核对实际端口绑定，不能只看 UFW 页面。[Docker 官方安全提示](https://docs.docker.com/engine/install/ubuntu/#firewall-limitations)
- 服务器必须能访问 GitHub、镜像仓库和依赖源；GitHub 的执行环境也必须能连到服务器 SSH。内网服务器不满足这一点时，需要另选经审查的连接方式，不要扩大防火墙到处放行。
- 域名 DNS 要指向服务器；准备有效 HTTPS 证书。证书申请、域名备案等条件取决于你的服务商和使用地区，本教程不假设已经自动完成。

**完成标志**：可以用部署账号 SSH 登录，基础工具可用，端口和域名情况已核对。安装失败时先停在本章，不继续叠加错误。

## 第三章：把代码、配置、业务数据分开

### 3.1 目录规划

以下是教程规划的目录，不是当前电脑上已经存在的文件：

```text
/opt/fastapiadmin-study/
├── repository/                   Git 仓库，只用于取得提交
├── releases/                     每次发布独立的程序目录
├── current                       指向最后一次验证成功的发布目录
├── previous                      指向上一成功版本（不包含数据库回滚）
├── shared/
│   ├── compose.env               Compose 参数和数据库等凭据
│   ├── backend.env               后端额外配置，例如 MAIL_*、DEBUG
│   ├── web.env                   前端构建配置，不能含秘密
│   ├── compose.server.yaml       服务器专用覆盖配置
│   ├── compose-functions.sh      统一的 Compose 调用函数
│   ├── nginx.conf                已替换域名的 Nginx 配置
│   ├── ssl/                      服务器证书和私钥
│   ├── mysql/                    MySQL 数据目录
│   ├── redis/                    Redis 数据目录
│   ├── uploads/                  公开上传目录
│   └── private-files/            项目私有附件
├── backups/                      数据库、附件等备份
└── deploy-release.sh             稍后编写的发布脚本
```

**为什么分开？** 每次发新版，只更换 releases 里的程序；配置和业务数据不会跟着替换。不要让上传文件依赖某一个发布目录。

在新服务器上，由管理员先创建 `/opt/fastapiadmin-study` 并授权给部署账号。然后以部署账号执行：

```bash
mkdir -p /opt/fastapiadmin-study/releases
mkdir -p /opt/fastapiadmin-study/shared/ssl
mkdir -p /opt/fastapiadmin-study/shared/mysql
mkdir -p /opt/fastapiadmin-study/shared/redis
mkdir -p /opt/fastapiadmin-study/shared/uploads
mkdir -p /opt/fastapiadmin-study/shared/private-files
mkdir -p /opt/fastapiadmin-study/backups
chmod 700 /opt/fastapiadmin-study/shared
chmod 700 /opt/fastapiadmin-study/backups
git clone https://github.com/1783334779/FastapiAdmin.git /opt/fastapiadmin-study/repository
```

路径若已有内容先核对归属，不覆盖。私有仓库请为服务器单独配置只读仓库访问凭据，不要把个人 GitHub token 写进 clone URL，也不要把服务器拉仓库的密钥和 GitHub 登录服务器的密钥混为一谈。

后端镜像运行用户 UID 为 1000。在新建的两个空上传目录上，由管理员执行下面的定向授权；不对整个项目递归改属主：

```bash
sudo chown 1000:1000 /opt/fastapiadmin-study/shared/uploads
sudo chown 1000:1000 /opt/fastapiadmin-study/shared/private-files
```

### 3.2 Compose 配置文件与应用环境变量不是一回事

用编辑器创建 `shared/compose.env`。从仓库 `docker/.env.example` 参考填写，至少核对：

```dotenv
APP_DOMAIN=learn.example.com
MYSQL_ROOT_PASSWORD=REPLACE_WITH_RANDOM_ROOT_PASSWORD
MYSQL_DATABASE=fastapiadmin
MYSQL_USER=fastapiadmin
MYSQL_PASSWORD=REPLACE_WITH_RANDOM_APP_PASSWORD
REDIS_PASSWORD=REPLACE_WITH_RANDOM_REDIS_PASSWORD
SECRET_KEY=REPLACE_WITH_RANDOM_SIGNING_KEY
DATA_ENCRYPTION_KEY=REPLACE_WITH_RANDOM_ENCRYPTION_KEY
DEPLOY_ENV=prod
BACKEND_IMAGE_TAG=first
LOGGER_LEVEL=INFO
DEMO_ENABLE=false
ALLOW_LOCALHOST_HOSTS=false
PROD_CORS_ORIGINS=https://learn.example.com
OAUTH_ALLOWED_HOSTS='["learn.example.com"]'
FORWARDED_ALLOW_IPS=10.255.178.0/24
SCHEDULER_ALLOW_CODE_EXEC=false
PRIVATE_FILE_DATA_DIR=/opt/fastapiadmin-study/shared/private-files
NGINX_TAG=stable-alpine
```

占位符必须替换，不能直接上线。可以用密码管理器分别生成随机值；不要让数据库口令、Redis 口令、签名密钥共用一个值，也不要在聊天或 CI 日志展示它们。示例 `stable-alpine` 方便学习，正式使用应选择当时受维护的 Nginx 镜像并固定经验证的版本或 digest，防止同名标签内容变化。

再用编辑器创建 `shared/backend.env`：

```dotenv
DEBUG=False
WORKERS=1
MAIL_ENABLED=False
MAIL_HOST=smtp.163.com
MAIL_PORT=465
MAIL_SECURITY=SSL
MAIL_USERNAME=你的邮箱@163.com
MAIL_PASSWORD='你的客户端授权码'
MAIL_FROM=你的邮箱@163.com
MAIL_FROM_NAME=项目管理系统
MAIL_TIMEOUT_SECONDS=10
```

首次部署可先保持邮件关闭，主功能正常后再开启。**本地已配置邮件，不代表服务器也有配置。** 不要上传整个本地 `.env.dev`。

创建 `shared/web.env`，这是公开的前端构建配置：

```dotenv
VITE_APP_ENV=production
VITE_APP_TITLE=项目管理系统
VITE_BASE_URL=/web/
VITE_APP_BASE_API=/api/v1
VITE_API_BASE_URL=http://127.0.0.1:8001
VITE_PORT=5180
VITE_API_TIMEOUT=15000
VITE_ACCESS_MODE=mixed
VITE_WITH_CREDENTIALS=false
VITE_OPEN_ROUTE_INFO=false
VITE_APP_WS_ENDPOINT=wss://learn.example.com
```

前端 `VITE_*` 会被打进浏览器可下载的 JS，不允许放密码或授权码。`VITE_API_BASE_URL` 在当前 Vite 配置中用于开发代理，生产接口请求主要取 `VITE_APP_BASE_API`，这里采用同域名 `/api/v1`。当前 WebSocket/SSE 客户端会以 `VITE_APP_WS_ENDPOINT` 为基础拼接实际接口路径，因此这里填写同一站点的 `wss://` 基地址；AI 聊天再拼接 `/api/v1/ai/chat/ws`。

设置文件权限：

```bash
chmod 600 /opt/fastapiadmin-study/shared/compose.env
chmod 600 /opt/fastapiadmin-study/shared/backend.env
chmod 600 /opt/fastapiadmin-study/shared/web.env
```

**新机制**：`docker compose --env-file xxx` 主要为 Compose 的 `${变量}` 提供值，不会自动把所有值传给后端。后端要收到 `MAIL_PASSWORD` 等，还需要服务上的 `env_file` 或明确 `environment`。下面的覆盖配置会完成这一步。[Docker 官方说明](https://docs.docker.com/compose/how-tos/environment-variables/set-environment-variables/)

### 3.3 复用现有 Compose，补服务器差异

用编辑器创建 `/opt/fastapiadmin-study/shared/compose.server.yaml`：

```yaml
services:
  backend:
    env_file:
      - /opt/fastapiadmin-study/shared/backend.env
    environment:
      APP_DOMAIN: ${APP_DOMAIN:?请配置实际域名}
      ALLOWED_HOSTS: '["${APP_DOMAIN:?请配置实际域名}"]'
      DEBUG: "False"
      WORKERS: "1"
    volumes:
      - /opt/fastapiadmin-study/shared/uploads:/home/static/upload
    healthcheck:
      test:
        - CMD
        - python
        - -c
        - >-
          import json, os, urllib.request;
          req = urllib.request.Request('http://backend:8001/api/v1/monitor/health/check', headers={'Host': os.environ['APP_DOMAIN'], 'X-Forwarded-Proto': 'https'});
          body = json.load(urllib.request.urlopen(req, timeout=5));
          assert body['data']['db_status'] == 1 and body['data']['redis_status'] == 1
  nginx:
    volumes:
      - /opt/fastapiadmin-study/shared/nginx.conf:/etc/nginx/nginx.conf:ro
      - /opt/fastapiadmin-study/shared/ssl:/etc/nginx/ssl:ro
volumes:
  mysql_data:
    driver_opts:
      device: /opt/fastapiadmin-study/shared/mysql
  redis_data:
    driver_opts:
      device: /opt/fastapiadmin-study/shared/redis
networks:
  app_network:
    ipam:
      config:
        - subnet: 10.255.178.0/24
```

需要先确认该网段不与服务器、VPN 或其他 Docker 网络冲突；冲突时要同时修改此处和 `FORWARDED_ALLOW_IPS`。不能把代理信任范围改成 `*` 来掩盖问题。

这里还修正了默认健康检查的两个学习陷阱：默认 Host 写死为原项目域名；默认 HTTP 成功不等于 DB/Redis 正常，当前接口即使其中一项失败也可能返回 HTTP 200。所以必须检查 JSON 的两个状态。探针通过容器网络访问，配合上面的可信代理网段处理 HTTPS 转发头。

多个 Compose 文件按顺序合并，同一容器挂载目标会被后面的对应配置替换。实际执行前必须验证合并结果。[Compose 合并规则](https://docs.docker.com/compose/how-tos/multiple-compose-files/merge/)

### 3.4 Nginx、域名和证书

把仓库 `docker/nginx/nginx.conf` 复制为服务器的 `shared/nginx.conf`，再用编辑器修改：

1. 把两个 `server_name service.fastapiadmin.com` 换成自己的域名。
2. 保留 `/web`、`/api/v1`、证书路径和转发头；不了解的缓存参数暂时不改。
3. HTTPS 证书完整链保存为 `shared/ssl/server.pem`，私钥保存为 `shared/ssl/server.key`，限制私钥读取权限。文件必须是实际证书和密钥，不是同名目录。
4. 接口文档默认不对公网开放，保留限制；不要为了 Swagger 调试而开放全部接口文档。

原配置含多个相同的隐藏文件拦截 location，Nginx 检查若报告 duplicate location，保留一个等价拦截并删除重复项；只修改服务器副本，先通过 `nginx -t` 再启动。这里是源码静态风险提示，尚未在服务器复现。

### 3.5 统一 Compose 命令，避免漏参数

创建 `shared/compose-functions.sh`，内容如下：

```bash
dc_for() {
  local release_dir="$1"
  shift
  docker compose --project-name fastapiadmin-study \
    --env-file /opt/fastapiadmin-study/shared/compose.env \
    -f "$release_dir/docker/docker-compose.yaml" \
    -f "$release_dir/docker/docker-compose.override.yaml" \
    -f "$release_dir/docker/docker-compose.attachments.yaml" \
    -f /opt/fastapiadmin-study/shared/compose.server.yaml \
    "$@"
}
```

后续每次使用它，都会同时带上域名、配置、私有附件和稳定的 Compose 项目名。不要中途换成裸 `docker compose up`，否则可能漏挂附件或连到另一套数据目录。

**完成标志**：这些服务器文件已经由你填写，真实凭据没有进入仓库，持久化目录与发布目录分离。

## 第四章：第一次手动部署

### 4.1 先把准备发布的代码提交并推送

在你自己的电脑上查看：

```bash
git status --short
git diff --stat
```

只选择你确认要发布的改动提交，不盲目 `git add .`。当前工作区有项目、里程碑、迁移和邮件等未提交改动；服务器拉 GitHub 不会得到这些未提交内容。

数据库迁移尤其需要审查：**已在某个数据库执行过的历史迁移，不应通过改旧文件来修改那个数据库结构，应增加新的增量迁移。** 当前有历史迁移文件的本地修改，在给已有数据库升级前必须核对，不能直接假定适合上线。

本地检查通过后，再提交并推送你选定的分支。本教程后续以 master 为例，不会替你执行提交或推送。

### 4.2 在服务器固定本次提交，创建独立发布目录

下面在部署账号的 Bash 终端中执行，并保留同一个终端的变量：

```bash
git -C /opt/fastapiadmin-study/repository fetch origin master
RELEASE_SHA=$(git -C /opt/fastapiadmin-study/repository rev-parse origin/master)
RELEASE_DIR=$(mktemp -d "/opt/fastapiadmin-study/releases/${RELEASE_SHA}.XXXXXX")
git -C /opt/fastapiadmin-study/repository archive "$RELEASE_SHA" | tar -x -C "$RELEASE_DIR"
printf '%s\n' "$RELEASE_SHA"
mkdir -p "$RELEASE_DIR/docker/mysql/init"
mkdir -p "$RELEASE_DIR/docker/nginx/web"
cp /opt/fastapiadmin-study/shared/web.env "$RELEASE_DIR/frontend/web/.env.production"
export BACKEND_IMAGE_TAG="$RELEASE_SHA"
source /opt/fastapiadmin-study/shared/compose-functions.sh
dc_for "$RELEASE_DIR" config --quiet
```

**为什么固定提交？** 发布中途即使你又 push 了代码，本次发布仍使用刚才记录的 SHA，不会前后端各拿到不同提交。

`config --quiet` 只检查配置，不启动容器。不要把完整 `docker compose config` 输出贴到聊天，它可能展开真实密码。

### 4.3 构建前端和后端

```bash
cd "$RELEASE_DIR/frontend/web"
pnpm install --frozen-lockfile
pnpm run build:prod
pnpm run type-check
pnpm run test
cd "$RELEASE_DIR"
cp -R frontend/web/dist docker/nginx/web/
dc_for "$RELEASE_DIR" build backend
```

**预期**：前端产生 `docker/nginx/web/dist/index.html`；后端产生 `backend:<提交 SHA>` 镜像。前端生产环境运行的是构建产物，不是 `pnpm dev`。

**第一排查点**：依赖下载失败检查网络；锁文件错误不要先删除锁文件；构建 OOM 检查内存；类型检查或测试失败应修正代码，不要为了发布跳过检查。

### 4.4 先启动依赖，再启动应用

只适用于确认过的空学习数据库；已有数据必须先读第六章完成备份和迁移审查。

```bash
dc_for "$RELEASE_DIR" up -d --wait --wait-timeout 180 mysql redis
dc_for "$RELEASE_DIR" run --rm --no-deps nginx nginx -t
dc_for "$RELEASE_DIR" up -d --wait --wait-timeout 240 backend nginx
dc_for "$RELEASE_DIR" ps
```

Nginx 检查证书、配置和可用性；如果此时报告 upstream `backend` 尚未存在，可先只启动 backend，待其健康后再检查和启动 nginx。不要无视配置检查错误继续发布。

`--wait` 等待容器就绪，但 Nginx 的容器健康检查主要是配置语法检查，不能证明外网浏览器访问成功，下一章仍要验证。

**数据库的重要实际行为**：当前 `backend/app/scripts/initialize.py` 会在启动时初始化空库，或对已有库运行 `alembic upgrade head`；dev 还会尝试生成迁移，prod 不会自动生成新的迁移文件。因此“重建后端”不一定只是换代码，也可能修改数据库。未知迁移版本还有清理逻辑，已有库发生这种告警时应停止核查迁移链，而不是把它当成正常修复手段。

**先预测一下**：如果你只改了模型、没提供对应增量迁移，生产数据库会自动知道该加什么字段吗？

答案：不能这样保证。prod 的启动会应用已经存在的迁移，不会替你自动生成缺少的迁移。

## 第五章：如何证明上线成功

### 5.1 从服务内部到浏览器，逐层验证

1. `dc_for "$RELEASE_DIR" ps`：容器在运行，backend 健康。
2. `dc_for "$RELEASE_DIR" logs --tail=100 backend`：没有反复重启、数据库迁移失败和权限错误。日志分享前脱敏。
3. 浏览器访问 `https://你的域名/web/`：页面能打开，刷新子页面不出现 404。
4. 正常登录：Network 中接口走当前域名的 `/api/v1`，不是 `localhost` 或本地开发端口。
5. 新建一个学习项目、读取详情；上传和下载一个无敏感信息的附件。
6. 重建一次应用后，项目和附件仍可访问，证明不只存于容器可写层。
7. 最后才开启服务器邮件配置，重建 backend，通过受保护接口主动发送测试邮件。

初次使用空数据库只会得到初始化数据，**不会自动带上你电脑中的项目、审批记录和附件**。数据迁移是单独的工作，需要匹配数据库版本、文件目录和加密密钥；不要直接把本地数据库覆盖到已有服务器库。

### 5.2 记录成功版本

确认 `current` 路径尚不存在或本来就是本教程创建的符号链接，再执行：

```bash
ln -sfn "$RELEASE_DIR" /opt/fastapiadmin-study/current
```

符号链接在这里是成功版本记录，不会神奇地让已经运行的容器自动切换。实际切换仍由 Compose 重建完成。

### 5.3 常见问题的第一排查点

| 现象 | 第一排查点 |
| --- | --- |
| 网页打不开 | DNS、安全组、80/443 占用、Nginx 状态和证书 |
| 打开根路径没页面，但容器正常 | 先访问 `/web/`，根路径对应的 docs 可能没有构建 |
| 页面空白或 JS 404 | `VITE_BASE_URL=/web/` 是否与 Nginx `/web` 一致，dist 是否放对位置 |
| 登录接口 404 | 前端 `/api/v1` 和 Nginx location 是否一致 |
| 接口 400 / Invalid host | 后端 `ALLOWED_HOSTS`、实际域名、健康检查 Host |
| 不停 HTTPS 重定向 | 可信代理网段是否与容器网段一致，是否正确传递协议头 |
| 接口 502 | 后端是否已启动并监听 8001，不能只看 Nginx 在运行 |
| 能查看但新增被拒绝 | `DEMO_ENABLE` 是否仍为 true；系统参数缓存也可能保存演示模式，要按现有参数管理流程核对 |
| 附件上传权限不足 | 宿主机上传目录是否可由容器 UID 1000 写入 |
| 重启后丢附件 | 私有附件叠加配置是否漏掉，实际挂载路径是否正确 |
| Redis 密码改了后不能登录 | 应用收到的密码是否一致；重启配置变更可能影响已有会话 |
| 邮件未开启/配置不完整 | 是否把 MAIL_* 真正传入后端，而不只是填进 Compose 参数文件 |

不要用 `chmod -R 777`、开放全部端口、禁用认证或关闭 TLS 校验作为通用修复。

## 第六章：备份、数据持久化和回滚

### 6.1 更新前先做什么

先确认本次是否包含数据库结构变化，再安排维护窗口或停止写入，检查备份并确认恢复方法。单纯“备份命令执行过”不等于一定恢复得回来。

在服务器上，从成功发布目录读取 Compose 配置做 MySQL 逻辑备份：

```bash
set -o pipefail
source /opt/fastapiadmin-study/shared/compose-functions.sh
ACTIVE_RELEASE=$(readlink -f /opt/fastapiadmin-study/current)
BACKUP_STAMP=$(date -u +%Y%m%dT%H%M%SZ)
umask 077
dc_for "$ACTIVE_RELEASE" exec -T mysql sh -c \
  'MYSQL_PWD="$MYSQL_ROOT_PASSWORD" exec mysqldump -uroot --single-transaction --routines --triggers --events --no-tablespaces "$MYSQL_DATABASE"' \
  | gzip > "/opt/fastapiadmin-study/backups/database-${BACKUP_STAMP}.sql.gz"
gzip -t "/opt/fastapiadmin-study/backups/database-${BACKUP_STAMP}.sql.gz"
```

这适用于本教程 Compose 自带的 MySQL，密码不直接拼在命令参数里。备份期间不要同时执行 DDL；`--single-transaction` 也不能承诺所有非事务表一致性。不要把备份输出到聊天或提交到 Git。

另外要备份公开上传、私有附件，以及受保护的配置和加密密钥。数据库与文件要在一致的业务时间点备份；有真实业务写入时，仅执行一条 tar 并不能保证一致性。备份还应有服务器之外的受控副本，并在隔离库演练恢复。

### 6.2 四种动作不要混淆

- 重启容器：通常仍运行原镜像，不等于发布新代码。
- 重建应用容器：换应用版本，应保留数据挂载。
- 回滚代码/镜像：换回上一版程序，**数据库不会自动变回去**。
- 恢复数据库备份：覆盖恢复点后的数据，是高风险动作，不能作为遇到错误就自动执行的步骤。

本教程不提供一键覆盖数据库的恢复命令，真实恢复前要确认目标库、备份时间、允许丢失的数据范围和文件配套关系。

### 6.3 只在数据库兼容时回滚应用

确认旧镜像、旧发布目录还在，且新数据库结构与旧代码兼容后，指定旧目录和旧 SHA：

```bash
source /opt/fastapiadmin-study/shared/compose-functions.sh
ROLLBACK_RELEASE=$(readlink -f /opt/fastapiadmin-study/previous)
export BACKEND_IMAGE_TAG=替换为上一成功版本的完整提交SHA
dc_for "$ROLLBACK_RELEASE" up -d --no-deps --wait --wait-timeout 240 backend nginx
```

验证成功后再更新 current/previous 记录。这是有条件的应用回滚，不承诺任何迁移都能自动撤销。如果新版本的配置也变过，还要恢复兼容配置；敏感密钥不要盲目回退或轮换。

**禁止当日常部署动作使用**：删除数据卷、重建数据库目录、全局 Docker 清理、强制重置包含服务器配置的 Git 工作区。尤其不要为了“干净重来”运行带删除数据卷选项的 Compose 停止命令。

## 第七章：把已验证的手动步骤封装成发布脚本

先只读懂职责，再保存到服务器的 `/opt/fastapiadmin-study/deploy-release.sh`。**仅在前面手动部署、备份和目录规划都通过后使用**；该脚本会真实更新应用，并可能触发数据库迁移。

这是单机学习版：服务器自己构建，需要额外 CPU、内存和网络；会有短暂中断。数据库变化先人工审查，在维护窗口使用。脚本失败后保留现场并返回失败，不自动清库、回滚数据库或清理旧镜像。

```bash
#!/usr/bin/env bash
set -Eeuo pipefail
umask 077

SHA="${1:-}"
if [[ ! "$SHA" =~ ^[0-9a-f]{40}$ ]]; then
  echo "必须传入完整的 40 位 Git 提交 SHA" >&2
  exit 1
fi

APP_ROOT=/opt/fastapiadmin-study
REPOSITORY="$APP_ROOT/repository"
source "$APP_ROOT/shared/compose-functions.sh"

# GitHub 限制之外再加服务器锁，手动和自动发布也不能同时改同一套服务。
exec 9>"$APP_ROOT/deploy.lock"
flock -n 9 || { echo "已有发布正在执行" >&2; exit 1; }

git -C "$REPOSITORY" fetch origin master
LATEST_SHA=$(git -C "$REPOSITORY" rev-parse origin/master)
if [[ "$SHA" != "$LATEST_SHA" ]]; then
  echo "这不是 master 当前最新提交，跳过过期的发布任务"
  exit 0
fi
git -C "$REPOSITORY" cat-file -e "$SHA^{commit}"

RELEASE_DIR=$(mktemp -d "$APP_ROOT/releases/${SHA}.XXXXXX")
git -C "$REPOSITORY" archive "$SHA" | tar -x -C "$RELEASE_DIR"
mkdir -p "$RELEASE_DIR/docker/mysql/init" "$RELEASE_DIR/docker/nginx/web"
cp "$APP_ROOT/shared/web.env" "$RELEASE_DIR/frontend/web/.env.production"
export BACKEND_IMAGE_TAG="$SHA"
dc_for "$RELEASE_DIR" config --quiet

cd "$RELEASE_DIR/frontend/web"
pnpm install --frozen-lockfile
pnpm run build:prod
pnpm run type-check
cd "$RELEASE_DIR"
cp -R frontend/web/dist docker/nginx/web/
dc_for "$RELEASE_DIR" build backend

for record in current previous; do
  if [[ -e "$APP_ROOT/$record" && ! -L "$APP_ROOT/$record" ]]; then
    echo "$record 不是符号链接，停止以免覆盖目录" >&2
    exit 1
  fi
done
if [[ ! -L "$APP_ROOT/current" ]]; then
  echo "请先手动完成首次部署并验证 current，再使用自动更新" >&2
  exit 1
fi
OLD_RELEASE=$(readlink -f "$APP_ROOT/current")
[[ "$OLD_RELEASE" == "$APP_ROOT/releases/"* ]] || exit 1

# 已审核迁移并进入维护窗口后才使用。先备份，再重建会执行迁移的后端。
BACKUP_STAMP=$(date -u +%Y%m%dT%H%M%SZ)
dc_for "$OLD_RELEASE" exec -T mysql sh -c \
  'MYSQL_PWD="$MYSQL_ROOT_PASSWORD" exec mysqldump -uroot --single-transaction --routines --triggers --events --no-tablespaces "$MYSQL_DATABASE"' \
  | gzip > "$APP_ROOT/backups/database-${BACKUP_STAMP}-${SHA}.sql.gz"
gzip -t "$APP_ROOT/backups/database-${BACKUP_STAMP}-${SHA}.sql.gz"

# backend 先启动，让 Nginx 配置检查可以解析到 backend 容器。
dc_for "$RELEASE_DIR" up -d --no-deps --wait --wait-timeout 240 backend
dc_for "$RELEASE_DIR" run --rm --no-deps nginx nginx -t
dc_for "$RELEASE_DIR" up -d --no-deps --wait --wait-timeout 120 nginx

# 后端容器健康检查还不等于外部 HTTPS 和前端访问正常。
APP_DOMAIN=$(dc_for "$RELEASE_DIR" exec -T backend printenv APP_DOMAIN)
curl --fail --silent --show-error --max-time 20 \
  "https://${APP_DOMAIN}/api/v1/monitor/health/check" \
  | python3 -c 'import json,sys; d=json.load(sys.stdin); assert d["data"]["db_status"] == 1 and d["data"]["redis_status"] == 1'
curl --fail --silent --show-error --max-time 20 \
  "https://${APP_DOMAIN}/web/" -o /dev/null

ln -sfn "$OLD_RELEASE" "$APP_ROOT/previous"
ln -sfn "$RELEASE_DIR" "$APP_ROOT/current"
echo "发布并验证完成：$SHA"
```

给脚本执行权限，并先用语法检查：

```bash
chmod 750 /opt/fastapiadmin-study/deploy-release.sh
bash -n /opt/fastapiadmin-study/deploy-release.sh
```

这时先不要接 GitHub。可以在一次有备份的学习更新中，自己传入准备好的完整 SHA 执行，核对更新记录和浏览器结果。非交互 SSH 的 PATH 可能不同：Node、pnpm、Docker 等必须在发布脚本运行环境可找到；不要依赖只在交互终端加载的 nvm。

**失败边界**：新后端已经启动但外网检查失败时，current 可能仍指向旧成功版本，运行中的服务却已经部分更新。失败意味着需要检查实际容器状态，不意味着线上完全没变化。备份只覆盖数据库，还必须按第六章保护文件并控制业务写入。正式业务要增加维护模式、数据库兼容发布和更完整的故障处理。

## 第八章：配置 GitHub 到服务器的安全连接

### 8.1 两种 SSH 身份分开

1. 你电脑到服务器：日常管理身份。
2. GitHub Actions 到服务器：单独创建的自动发布身份。

如果服务器拉的是私有 GitHub 仓库，还需要服务器到仓库的只读凭据，这是第三条连接，不要复用个人私钥。

为自动发布创建专用密钥，使用新的文件名，已有同名文件时不要覆盖。公钥添加到服务器部署账号的 `authorized_keys`；私钥只进入 GitHub Secrets，不提交仓库。按需限制 SSH 转发、来源和账号权限；密钥泄露时立即撤销。

### 8.2 配置 Secrets

在仓库网页进入 `Settings → Secrets and variables → Actions`，添加：

| 名称 | 内容 |
| --- | --- |
| `DEPLOY_HOST` | 服务器 IP 或 SSH 域名，不带协议 |
| `DEPLOY_PORT` | SSH 端口 |
| `DEPLOY_USER` | 专用部署账号 |
| `DEPLOY_SSH_KEY` | 自动发布专用私钥 |
| `DEPLOY_KNOWN_HOSTS` | 经过核实的服务器 SSH 主机公钥记录 |

主机公钥与登录私钥不是同一个东西。先通过云控制台等可信通道核对服务器主机公钥指纹；`ssh-keyscan` 获取的内容未经核对不能直接当成可信身份。不要使用 `StrictHostKeyChecking=no` 跳过验证。[GitHub Secrets 官方说明](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-secrets)

数据库、Redis、邮箱凭据继续只放在服务器配置文件里，GitHub 本次不需要拿到这些凭据。

### 8.3 先建立可复用的检查入口

当前前后端 CI 和密钥扫描是独立工作流。**另建一个 push 工作流，不会自动等它们成功。** `needs` 也不能直接引用另一个工作流里的 job。

在准备启用教程自动化时，手动给现有以下三个工作流的 `on:` 下增加 `workflow_call:`，保留原有触发条件：

- `.github/workflows/backend-ci.yml`
- `.github/workflows/frontend-ci.yml`
- `.github/workflows/secrets.yml`

后端 CI 中的 Ruff 建议改为 `uv run ruff check --no-fix`，避免在 CI 中修好了工作区却部署未经修复的原提交。

密钥扫描工作流目前对手动触发缺少 before 值的处理，复用之前把原有 RANGE 判断替换为：

```bash
if [ "${{ github.event_name }}" = "pull_request" ]; then
  RANGE="${{ github.event.pull_request.base.sha }}..${{ github.event.pull_request.head.sha }}"
elif [ -n "${{ github.event.before }}" ] && [ "${{ github.event.before }}" != "0000000000000000000000000000000000000000" ]; then
  RANGE="${{ github.event.before }}..${{ github.sha }}"
else
  RANGE="-1"
fi
```

沿用原扫描命令和已固定的下载校验。这段是 GitHub Actions `run` 内的模板，**不是可以直接粘贴到服务器终端的 Bash**。对于新建分支首次推送，`-1` 只扫描最后一个提交，不能代替对整个首次发布源码的凭据检查；发布前仍需确认当前代码不含凭据，发现历史泄露还需要轮换旧密钥。

上次本地回归有两处原有测试断言与附件/里程碑改动不一致，开启自动发布前先处理并让检查真实通过，不跳过失败用例。这里不自动修改现有测试或 CI 文件。

## 第九章：从手动触发 Actions，过渡到 push 自动发布

### 9.1 先手动触发，不急着绑定每次 push

完成前面各章后，才在仓库手动创建 `.github/workflows/deploy-study.yml`。模板先只有 `workflow_dispatch`；在 master 上手动触发，确认成功后再按下一节开启 push。

```yaml
name: deploy-study

on:
  workflow_dispatch:

permissions:
  contents: read

jobs:
  verify-backend:
    uses: ./.github/workflows/backend-ci.yml
  verify-frontend:
    uses: ./.github/workflows/frontend-ci.yml
  verify-secrets:
    uses: ./.github/workflows/secrets.yml

  deploy:
    needs: [verify-backend, verify-frontend, verify-secrets]
    if: github.ref == 'refs/heads/master'
    runs-on: ubuntu-latest
    timeout-minutes: 45
    environment: production
    concurrency:
      group: fastapiadmin-study-production
      cancel-in-progress: false
    steps:
      - name: 发布指定提交
        shell: bash
        env:
          DEPLOY_HOST: ${{ secrets.DEPLOY_HOST }}
          DEPLOY_PORT: ${{ secrets.DEPLOY_PORT }}
          DEPLOY_USER: ${{ secrets.DEPLOY_USER }}
          DEPLOY_SSH_KEY: ${{ secrets.DEPLOY_SSH_KEY }}
          DEPLOY_KNOWN_HOSTS: ${{ secrets.DEPLOY_KNOWN_HOSTS }}
          DEPLOY_SHA: ${{ github.sha }}
        run: |
          set -euo pipefail
          test -n "$DEPLOY_HOST"
          test -n "$DEPLOY_PORT"
          test -n "$DEPLOY_USER"
          test -n "$DEPLOY_SSH_KEY"
          test -n "$DEPLOY_KNOWN_HOSTS"
          [[ "$DEPLOY_PORT" =~ ^[0-9]+$ ]]
          [[ "$DEPLOY_SHA" =~ ^[0-9a-f]{40}$ ]]
          SSH_DIR=$(mktemp -d "$RUNNER_TEMP/fastapiadmin-ssh.XXXXXX")
          chmod 700 "$SSH_DIR"
          printf '%s\n' "$DEPLOY_SSH_KEY" > "$SSH_DIR/id_ed25519"
          printf '%s\n' "$DEPLOY_KNOWN_HOSTS" > "$SSH_DIR/known_hosts"
          chmod 600 "$SSH_DIR/id_ed25519" "$SSH_DIR/known_hosts"
          ssh -i "$SSH_DIR/id_ed25519" -p "$DEPLOY_PORT" \
            -o BatchMode=yes -o ConnectTimeout=15 \
            -o ServerAliveInterval=15 -o ServerAliveCountMax=4 \
            -o StrictHostKeyChecking=yes \
            -o UserKnownHostsFile="$SSH_DIR/known_hosts" \
            "$DEPLOY_USER@$DEPLOY_HOST" \
            "/opt/fastapiadmin-study/deploy-release.sh $DEPLOY_SHA"
```

这不会绕过现有检查，而是复用它们作为前置条件。[工作流语法与 needs](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax)

需要在 GitHub 配好 `production` 环境。如果当前仓库类型和套餐支持，建议先设置发布审批，特别是包含数据库迁移的发布；不支持时保留手动触发，不能把一个未配置的 environment 名称误认为“已经有人审核”。[环境与保护规则](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments)

首次运行时在 GitHub `Actions` 页面选中该工作流，选择 master 执行，观察每个检查 job 和 deploy 的日志。若失败，先确认失败在哪一层，不要连续点重试碰运气。

### 9.2 检查通过后再加 push

把该工作流的触发部分改为：

```yaml
on:
  push:
    branches: [master]
  workflow_dispatch:
```

现在你向 master 推送，才会自动触发；只在电脑 `git commit` 不会触发。合并其他分支到 master 并推送，也属于 master 更新。[push 触发说明](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#push)

你可以取消普通学习更新的人工审批，但涉及不兼容迁移、配置切换和重要数据时仍应设置门禁，不应承诺所有提交都能无条件自动上线。

### 9.3 最容易误解的五件事

1. **检查和发布必须对应同一个 SHA**，不是“随便一个 CI 绿了，就部署最新代码”。这里 GitHub 传入 `github.sha`，服务器构建该提交；若它已落后于 master，会跳过，避免旧任务晚到覆盖新版本。
2. `cancel-in-progress: false` 避免为新推送强行打断正在发布的 SSH 操作；默认并发组只有一个运行和一个等待项，中间等待任务可能被更新任务替代，并不是保证每次提交都逐一发布。[并发控制说明](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency)
3. GitHub 任务失败或 SSH 超时，不保证远端脚本立刻停止；查服务器锁、进程、容器和发布记录后再决定重试。不要同时手动补发。
4. 第七章脚本的数据库备份不是自动回滚系统；迁移失败可能已改变部分结构，尤其 MySQL 的某些 DDL 不受普通事务完整回滚保护。
5. 初期复用原有工作流可能导致 push 时独立 CI 和被调用 CI 重复运行，先保证门禁正确，再考虑调整触发方式以减少重复。不要用 `workflow_run` 随意拼接带凭据的部署，避免来源、提交对应关系和权限边界变复杂。

## 第十章：学完之后，再考虑的扩展

下面都不是完成本次学习的条件：

- 在 GitHub 构建镜像和前端产物，服务器只接收版本化产物，减少服务器构建压力。
- 将镜像放进有权限控制的镜像仓库，固定 digest，改善可重复性。
- 测试环境与生产环境分离，先测试后提升同一份产物。
- 蓝绿发布或反向代理切换，降低应用更新中断；数据库仍需兼容演进。
- 使用 Docker secrets 或外部密钥管理服务。当前 env_file 方案便于学习，但具有 Docker 管理权限的用户仍可能查看容器环境，不等于密钥完全不可见。
- 监控、告警、备份异地保存、恢复演练、证书自动续期。
- 额外模块的本地文件/SQLite 数据也要单独核对持久化，不能认为 MySQL 与项目附件已持久化就覆盖了整个系统所有数据。
- 定期检查依赖、基础镜像和 GitHub Actions 版本，正式环境把第三方 Actions 固定到经过核实的完整提交 SHA。
