# 项目与审批流程：按业务主线学习

依据：2026-10-26 当前工作区源码。本文是学习安排，不是待开发需求；未修改业务代码、数据库或基础设施。

## 学习方式

- 每次讲完一章，每章围绕一个完整业务结果。你不需要写代码，看懂后再进入下一章。
- 固定顺序：整体功能 → 已有前提 → 一个核心新机制 → 源码阅读路线与停止点 → 操作、预期、第一排查点。
- 页面只用于观察请求和结果，后端是重点；不要求先学 Vue、整个 FastAPI 框架或全部数据库封装。
- 暂时跳过的代码会明确指出，后面的章节再回来解释。扩展、思考题、异常实验都不是继续条件。
- 解释异常前先给预测机会，可以只在心里判断。不要为了验证异常而破坏现有流程、角色或正式数据。
- 源码推断、自动测试证据、当前页面的实际运行结果分别说明，不混为一谈。

配套操作说明：[项目模块与审批流程使用说明](项目模块与审批流程使用说明.md)。原来的《后端学习计划》继续作为通用后端基础教材，本文件专门学习项目与审批流程的协作。

## 总体地图

| 部分 | 负责什么 | 不负责什么 |
| --- | --- | --- |
| 项目模块 | 项目字段、经理名单、资料版本、创建修改和业务状态 | 不在创建函数里写死整条审批路线 |
| 流程配置模块 | 保存图、节点规则、业务角色、发布版本和模块绑定 | 保存一张图不等于给某个项目生成待办 |
| 流程运行部分 | 为某张项目生成实例，执行节点、找人、生成待办并处理审批 | 不应代替项目模块维护所有业务字段 |

三者目前都在同一个后端应用中。Service 之间是 Python 函数调用，不是三个独立服务通过 HTTP 互相请求。

## 章节安排

### 第 1 章：点击“提交审批”，项目和流程第一次怎样接上

- 功能与成果：看懂页面的一次提交如何进入后端，为什么不需要用户先保存草稿。
- 已有前提：能分辨接口 Controller 与业务 Service；知道当前用户填写的是具体经理人员。
- 核心新机制：业务编排——一个 Service 方法组织“创建项目”和“发起流程”，二者使用同一个数据库会话。
- 阅读：`ProjectEditor.vue:save` → `projectApi.createAndSubmit` → `project_create_submit` → `ProjectService.create_and_submit`。读到该方法返回即停，不进入 `WorkflowService.submit` 内部。
- 暂跳：编辑页分支；人员和字典选项加载；幂等键内部算法；行锁细节；`create` 和 `submit` 的内部实现。
- 操作/预期：在有有效配置的学习环境，用学习单据直接提交；Network 中本次写请求为 `POST /business/project/create-and-submit`，正常串行流程返回项目 `IN_REVIEW`。不要误把页面加载的查询请求也算成提交写请求。
- 第一排查点：没有发请求先查表单校验与确认框；403 查创建及提交两项权限；业务失败看响应中的具体错误，再追 Service。

### 第 2 章：一张项目为什么要用三张表保存

- 功能与成果：看懂字段、多个经理、资料历史版本分别怎样落库，区分创建草稿与提交审批。
- 已有前提：第 1 章；本章可以只观察自己的学习草稿，不要求发起审批。
- 核心新机制：资料快照——当前项目与“当时提交/审阅的资料”分开保存。
- 阅读：`business/project/schema.py:ProjectCreateSchema` → `ProjectService.create/validate_input` → `ProjectCRUD.create_draft` → `ProjectService.save_revision/serialize`；需要辨认字段时对照 `model.py` 三个模型。读到创建响应即停。
- 暂跳：列表权限、更新删除、复杂 ORM 基类、流程引擎。
- 操作/预期：保存学习草稿，看到 `DRAFT`、资料 v1、经理用户 ID；尚未出现审批待办。
- 第一排查点：格式失败看 Schema；人员/部门/字典失效看 `validate_input`；当前资料指针看 `save_revision`。

### 第 3 章：项目怎样找到绑定流程，并把资料交给它

- 功能与成果：解释你之前问的“我的流程怎么绑定项目”，以及发布新版本为何不改变已提交项目。
- 已有前提：区分项目资料版本与流程发布版本；管理员已有发布和绑定配置。
- 核心新机制：适配器——向运行部分提供项目资料，并把流程状态映射回项目状态。
- 阅读：`WorkflowService.set_binding/binding` → `version_for_project` → `adapters.py:adapter_for` → `ProjectWorkflowAdapter.load/context/sync_status` → `WorkflowService.submit` 的调用位置。看到选定版本和交付资料即停。
- 暂跳：`submit` 中的节点执行、锁实现、幂等计算。已有实例路径与首次提交路径都要看，不把“第一版”误解成永远使用版本号 1。
- 操作/预期：只读检查绑定、已发布版本和学习项目历史；首次提交采用当时绑定的发布版，此项目后续沿用该版。
- 第一排查点：未提交项目看绑定、流程启用状态和发布指针；已提交项目先看实例 `version_id`，不是只看当前绑定。

### 第 4 章：业务角色如何变成具体人，并生成第一批待办

- 功能与成果：解释“表单选了经理”和“经理真的收到待办”之间发生了什么。
- 已有前提：第 3 章中的发布版、项目上下文；先使用简单串行流程。
- 核心新机制：找人规则解析——业务角色是规则入口，待办才明确分配给某个用户。
- 阅读：`WorkflowService.submit` → `AssigneeResolver.precheck/resolve` → `users/role_users/department_managers` → `WorkflowRuntime.start/spawn/activate` 的 START、审批分支 → `persist`。看到首个 visit 与人员 task 创建即停。
- 暂跳：条件、并行、结束汇总、驳回和恢复。`activate` 的最后 `else` 在已校验图中承担审批节点处理，并非任意未知类型都应当成为审批节点。
- 操作/预期：提交自己的学习单据，首节点人员从“我的待办”看到任务；后续串行节点不会提前生成待办。预检会检查全图，但预检本身不创建任务。
- 第一排查点：提交报缺人看预检节点；提交成功却找不到任务，看当前节点、解析出的用户 ID、任务归属和状态。

### 第 5 章：点一次“通过”，为什么会走到下一个节点

- 功能与成果：跟完一条普通串行审批，理解任意一人通过与所有人通过。
- 已有前提：有当前用户自己的有效任务；已经分清图上的节点、一次节点执行 visit、个人待办 task。
- 核心新机制：状态迁移——完成个人任务不一定立即完成节点，完成节点也不一定结束整个项目。
- 阅读：`task_approve` → `WorkflowService.decide/locked_task` → `WorkflowRuntime.approve/complete_mode/forward/activate` → `persist` → `adapter.sync_status`。到下一个待办或 END 完成为止。
- 暂跳：`decide` 的 reject 分支；`complete_mode` 的返回模式；复杂并行；并发防护内部原理。
- 操作/预期：办理学习单据的本人任务；ANY 首人通过关闭同次剩余待办，ALL 等全部通过，末节点结束后项目才为 `APPROVED`。
- 第一排查点：任务已通过却没推进，先检查 ANY/ALL 配置、同次 visit 的其他任务，而不是仅看项目状态。

### 第 6 章：画出来的流程图，后端实际保存了什么

- 功能与成果：把界面上的节点和连线，对应到发布后引擎读取的图数据。
- 已有前提：先看懂简单流程怎样运行，再回头学习它从哪里来。
- 核心新机制：配置与发布分离——可编辑草稿不直接替换运行中的发布版。
- 阅读：前端 `module_system/approval_flow/designer.vue` 作为入口定位 → `flow_create/flow_update/flow_validate/flow_publish` → `WorkflowService.save_definition/validate_definition/frozen_rules/publish` → `graph.py:validate_graph` → `WorkflowVersionModel`。看到新发布版本和发布指针即停。
- 暂跳：VueFlow 绘图内部原理、拖动坐标细节、图校验的复杂并行算法。
- 操作/预期：优先只读现有配置；需要实验时另建学习流程，不替换当前项目绑定。保存草稿与发布版是两个概念。
- 第一排查点：页面改了但运行未变，查是否保存、发布、绑定，以及该项目是否早已固定旧版。

### 第 7 章：条件分支和并行分支怎样执行

- 功能与成果：看懂只走一条的条件分支，以及多条分支都结束才继续的汇合。
- 已有前提：第 4～6 章；图必须通过结构校验。
- 核心新机制：执行标记与并行作用域——记录当前走到哪一条分支，而非统计整张图有几个节点通过。
- 阅读：`graph.py:validate_condition/evaluate` → `WorkflowRuntime.activate` 的 EXCLUSIVE/PARALLEL/JOIN → `state.scopes` 的 expected/arrivals → `persist`。读到分支汇合并生成下一待办即停。
- 暂跳：嵌套返回；先讲一个条件和两路并行，再解释嵌套的作用域，不要求背递归算法。
- 操作/预期：使用隔离测试案例观察；条件按优先级首次命中且有默认路，并行未到齐不推进。
- 第一排查点：条件看实际字典 value/布尔类型、优先级和 routes；并行看本次作用域 expected/arrivals，不数全部历史任务。

### 第 8 章：驳回重走与定点返回为什么是两套行为

- 功能与成果：跟完 D→B→D、D→起草→D，以及重走从开始的区别。
- 已有前提：知道 visit 可以重复产生，图本身不能通过画回环代替驳回。
- 核心新机制：返回链——临时处理完目标后，恢复原审批位置；嵌套退回逐层返回。
- 阅读：`task_reject` → `WorkflowService.decide` 的 reject 分支 → `WorkflowRuntime.targets/reject/suspend` → `resubmit_targeted/complete_mode/resume`；重走再看 `start` 的旧轮归档。分别以一条实例轨迹读完，不同时脑补全部分支。
- 暂跳：高级并发实现；跨分支目标不允许，不把它当作待补功能。
- 操作/预期：使用学习单据或隔离案例；只退起草时可改资料，D→B 后 B 通过直接回 D；重走不选目标且从开始走。
- 第一排查点：模式、目标 visit、返回链和轮次；不能仅凭节点名字判断这一次应当回哪里。

### 第 9 章：缺人、暂停、恢复和撤回怎样收尾

- 功能与成果：理解提交时有人为什么不保证以后永远有人，以及哪些操作可恢复、哪些不能撤回。
- 已有前提：提交预检、进入节点重新找人、同次 visit 名单冻结。
- 核心新机制：明确的异常状态——失败不是随便跳过审批，也不等于丢掉已完成进度。
- 阅读：`WorkflowRuntime.block/retry/suspend/resume/cancel_open` → `WorkflowService.recover/withdraw/terminate_for_delete`。看到状态回写及审计记录即停。
- 暂跳：生产故障注入；不改真实成员或停用账号来制造实验。
- 操作/预期：隔离案例中激活缺人暂停，修复后恢复；冻结会签成员失效不能自动删掉该人的责任；实例已有手动审批/驳回不能撤回。
- 第一排查点：blocked.kind 是激活缺人还是冻结成员失效，再决定修哪里，不能一律改角色后重试。

### 第 10 章：谁能看项目，历史资料与审批记录怎样对上

- 功能与成果：分清项目列表权限与个人任务查看入口，解释审批究竟针对哪版资料。
- 已有前提：创建部门快照、项目资料 revision、节点 visit 和个人 task。
- 核心新机制：对象级授权——有接口权限，不等于能查看所有项目或处理所有任务。
- 阅读：`ProjectService.page/detail/visible_condition/get_visible` → `managed_department_ids` → `WorkflowService.task_page/task_detail/business_history` → 各模型的 revision/decision_revision_id。到列表、任务详情和历史返回数据为止。
- 暂跳：登录 Token 和全局权限系统实现；不要把测试里的认证替换理解成生产绕过鉴权。
- 操作/预期：学习账号分别观察创建人、负责人、普通审批人入口；审批人可从本人待办/已办查看单据，不因此得到部门全部项目权限。
- 第一排查点：先确定访问的是项目详情还是个人任务，再查创建人、创建部门管理范围或 assignee_id。

### 第 11 章：怎样避免重复提交、半成功和覆盖别人的操作

- 功能与成果：回头解释主线里曾暂时跳过的 command_key、expected_version、行锁和 flush。
- 已有前提：已经能跟完正常的提交和审批，不要求先掌握数据库所有隔离级别。
- 核心新机制：一条写命令的安全边界——事务、幂等、版本和锁解决的是不同问题，不能互相替代。
- 阅读：`db_getter` → `ProjectService.create_and_submit/update_and_submit` → `WorkflowService.cached_command/remember/locked_task/decide` → `ProjectWorkflowAdapter.load`。读到成功提交或异常整体回滚的边界即停。
- 暂跳：修改全局数据库配置；真实库并发压测；哈希算法数学细节。
- 操作/预期：隔离集成测试中，同内容同键返回同一结果，不重复建单；改内容复用键冲突；资料或版本过期拒绝；发起失败不遗留半张新项目。
- 第一排查点：超时先核对同键重试；409 核对请求内容和两种版本；读回旧资料指针检查 autoflush 与显式 flush。

### 第 12 章：换成采购单等新模块，哪些能复用、哪些必须开发

- 功能与成果：把所学转成真实模块开发清单，而不是误以为画图就能接入所有业务。
- 已有前提：前面各章的项目契约、发布版、适配器、找人和运行记录。
- 核心新机制：扩展契约——业务提供资料、身份与状态映射，流程提供执行能力。
- 阅读：`adapters.py` 注册表 → 项目 Adapter 三个方法 → `WorkflowService` 中项目专属调用 → `resolvers.py:USER_FIELDS/validate_business_rule` → `bootstrap.py` → 本模块迁移与 `tests/test_project_workflow.py`。整理职责清单即停，不自动开发第二个模块。
- 暂跳：生产部署、基础设施改造、把当前实现重构为通用平台；这些不是学完的前提。
- 操作/预期：只做源码分析和清单，不要求新增真实业务。明确当前已复用图执行，但提交服务仍直接引用项目 Schema/Service、绑定及人员字段也有项目限定，不能说“只注册 Adapter 就完成新模块”。
- 第一排查点：逐项搜 `project` 和人员字段白名单，区分真正通用的引擎与仍需改造的业务耦合。

## 第 1 章讲解卡

### 先看整体功能

用户在创建页填写项目名称、类型、经理等资料后，有两个选择：

| 按钮 | 业务结果 | 是否产生审批待办 |
| --- | --- | --- |
| 保存草稿 | 保存项目及资料 v1，状态 DRAFT | 否 |
| 提交审批 | 创建项目、选择流程版本、检查找人、启动流程；正常简单串行下项目为 IN_REVIEW | 首个审批节点产生待办 |

“直接提交”不是不保存项目，而是用户不必先操作一次保存。后端仍要先得到项目 ID 和资料，再为它发起流程；这些步骤属于同一次请求事务。

### 已有前提

创建人有有效部门；经理、业务部门与字典值有效；管理员已经发布并绑定流程；节点可以找到有效审批人；用户同时有创建与提交权限。这里只列前提，不要求现在先钻进它们的实现。

### 一个核心新机制：编排

创建项目不是流程引擎的全部工作，流程引擎也不是创建接口里的几行固定审批判断。`ProjectService.create_and_submit` 作为编排方法，先调用创建能力，再调用发起流程能力，最后返回项目的最新状态。

```text
创建页 save("submit")
  → projectApi.createAndSubmit(表单, 命令键)
  → project_create_submit(请求数据, 当前用户, 数据库会话)
  → ProjectService.create_and_submit
      → create：校验并创建项目资料
      → flush：把待写内容刷新进当前数据库事务
      → WorkflowService.submit：为这个项目发起审批
      → serialize：组装项目当前数据
  → 返回项目结果，页面跳详情
```

这表示请求中的关键业务调用关系，不是说所有基础设施只有这些函数。权限依赖、日志、事务结束等仍由现有框架接入。

### 本章逐步看什么

1. 前端 `ProjectEditor.vue:save`：只看 action 为 submit、没有 projectId 的路径。它检查表单、让用户确认，再调用 `createAndSubmit`。没有先调用保存草稿接口。
2. `project.ts:createAndSubmit`：确认地址与请求体。字段之外带 `command_key`，本章先理解为本次命令标识，详细原理放第 11 章。
3. 后端 `controller.py:project_create_submit`：输入由 `ProjectCreateSubmitSchema` 声明，db 由依赖提供，两个权限依赖分别检查创建和提交；然后交给 Service。不要把这里理解成已经生成了待办。
4. `ProjectService.create_and_submit`：`create(data)` 返回已创建项目的数据，其中有项目 ID；`flush()` 先刷新本事务中的写入，避免随后重新读取时丢失尚未刷新的资料指针；它不是最终提交事务。
5. `workflow.submit(created["id"], ...)`：这里是项目模块进入流程运行部分的连接点。传的是项目 ID 和命令信息，不是由前端把整张图发过来。本章把它视为“为该项目发起流程”，第 3～4 章再展开。
6. 再次加载并序列化项目：不能直接返回启动前的 `created` 数据，因为流程启动后项目状态已经变化。返回最新结果后，本章停止。

### 操作、预期与异常预测

按使用说明先有有效配置，再对自己的学习单据点击“提交审批”，确认后观察 Network；本章不要求新增或改变流程配置。

- 正常预期：本次创建提交是一个写请求；响应项目为 IN_REVIEW；进入项目详情。首节点待办的生成内部留到第 4 章。
- 先预测：假如所有表单字段都有效，但模块没有绑定已发布流程，直接提交失败后，会留下一张草稿吗？可以只在心里判断，不需要实际解绑流程。
- 再解释：不会。创建与启动共享请求事务，启动异常使这次创建一起回滚。这与“保存草稿”不同，单独保存草稿不要求已经绑定流程。
- 第一排查点：报未绑定流程时看 `version_for_project`；不要先怀疑经理字段保存丢失。

### 当前文案与实现的一个差异

`ProjectWorkflowAdapter.context` 在缺失资料版本时仍提示“项目尚无完整资料版本，请先保存草稿”。这段提示不能被理解为用户必须先点保存草稿：当前直接提交路径会在同一事务中创建资料并刷新，再发起审批。它更准确表达的是“缺少资料版本”；此次学习仅指出文案局限，不修改业务代码。
